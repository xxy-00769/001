# FPGA_GSV1 开发方案 V2：三个 FPGA 主里程碑，再做协同识别

更新日期：2026-10-21。替代《FPGA优先开发方案与阶段验收》中S0～S14的实施顺序。M2已上板验收；M3-01已实现并获得四路显示/前摄上传初步实物反馈，以下最新补充优先于正文历史计划。

## 最新补充：显示器与双网口分工

- 显示器改为普通1920×1080显示器，不再以MPI7001小屏作为后续输出目标。M3-02负责标准1080p输出适配、真实视频文件右摄及软件发送性能，原始采集/DDR/网络像素仍1280×720 RGB565。
- 当前网口1暂时共用右摄输入、前摄上传和控制，用电脑完成联调。最终网口1保留电脑/视频源右摄输入，网口2连接香橙派，承载前摄原图、按键事件、判定/告警及相应心跳/ACK。
- M3-02通过后进行M3双网口分流与上板闭环，再进入M4真实识别。两个端口的会话/失联状态独立；迁移前摄网络读者，不无故复制读者和DDR流量。
- 用户截图初步显示前摄约4.96fps、右摄约1.08fps、缺包及不完整帧0；全部网络异常恢复、长期稳定和目标吞吐尚未全量验收。
- M3-02 3.1上板显示“输入不支持”；此前允许1080p30的条件撤销。当前优先[M3-03 HDMI兼容性修复](prompts/M3_03_hdmi_compatibility_fix.md)，以27B1已知可用的1080p60为目标，恢复显示后再继续M3分流。历史任务见[M3-02开发提示词](prompts/M3_02_hd_display_real_video.md)。

## 1. 已确定的输入映射和范围

| 物理输入 | 固定用途 | 初期实现 |
| --- | --- | --- |
| 双目模组 CAM0 | 前摄 FRONT | 干净彩色采集、板上显示、独立网口上传 |
| 双目模组 CAM1 | 后摄 REAR | 用户延长排线布置到后方，独立采集与显示 |
| HDMI-IN | 左摄 LEFT | 接收左视角视频，转换成统一像素格式 |
| 网口 VIDEO_IN | 右摄 RIGHT | 接收电脑/ARM 解码后发送的右视角像素流 |

前后摄按用户布置确定，不再作为待讨论的方位映射问题。代码集中保存这张映射表，正常模式固定使用，不额外开发运行时映射菜单。

后摄链路在 M1 就使用计划中的延长排线测试，以短线作为排错对照，验证实际长度下的采集稳定性。共享时钟源不等于曝光同步；四宫格先允许使用各路最新完整帧，同步与标定留给后续全景。

本期 FPGA 目标：四路独立采集、四个单视角和四宫格、KEY5 切换、中文、KEY6 基础处理、前摄原彩色图上传、按键/判定通信及 LED 反馈。

道路区域、车道线/实虚线、斑马线、道路类型等改为 FPGA 与香橙派协同开发，不再要求先在 FPGA 单独实现完整道路理解。全景在四宫格稳定后启动，不阻塞主系统联调。

## 2. 提高效率的具体做法

1. **第一份交付直接显示双摄实景。** 工程整理、彩条、单摄接通是内部检查点，合并进 M1，不各自成为等待用户反馈的独立大版本。
2. **从第一天使用统一的四路接口。** 共用帧描述符、缓存管理、DDR 调度、缩放显示和状态统计。先接双摄，随后增加两个输入适配器，不经历“单路专用→双路专用→四路重写”。
3. **按模块复用稳定实现。** 提取已适配板卡的 DDR/IP、摄像头配置、HDMI 和有效缓存修复及对应检查；不重写成熟驱动，也不整包复制旧工程。不为整理目录重新生成厂商 IP。
4. **基础处理只集成一遍。** 统一放在视图选择/合成之后，M2 一次接入灰度、滤波、二值、色彩空间与 KEY6，后续四路复用。
5. **网络三种业务一起接同一协议栈。** 右摄接收、前摄发送、按键/反馈共用 MAC/IP/UDP、调度和统计；分模块验证，M3 合并交付。电脑端做一个联调工具，后来香橙派直接复用收发代码。
6. **先让真实视觉进入系统，再决定硬件加速。** M3 控制回路通过即可进入香橙派识别；根据效果和耗时补 FPGA 特征，不先重复实现一套完整语义算法。
7. **每个里程碑完成时做组合验证。** 内部改动用有针对性的仿真、参考图比对和增量构建；只在接口接入、关键改动或里程碑交付时进行必要上板检查。首次单摄及首次网络仍要分别确认，不能为合并版本跳过硬件问题定位。

减少的是重复实现、重复集成和独立交付次数，实际吞吐、时序、帧完整性与断流恢复仍需验证。暂不承诺日历工期；板卡反馈和编译结果会影响实际进度。

## 3. 开发顺序

```text
M1 双摄实景 + 统一缓存/显示框架 + 按键/中文/LED
  ↓
M2 HDMI左摄 + 四宫格显示结构 + KEY6基础处理
  ↓
M3 网口右摄接收 + 前摄原图发送 + 按键/判定控制
  ↓
四路四宫格稳定，发布 FPGA 基础版本
  ↓
M4 香橙派道路理解与驾驶规则，结果回传 FPGA

M5 全景融合：四宫格稳定后独立启动，按视角和标定条件实施
```

M5 的启动依赖 M3 的四路完整帧和稳定四宫格；不要求等待 M4 全部算法完成，也不要求 M4 等待全景完成。具体投入按主系统演示进度安排。

### M1：双摄实景显示，建立后续可扩展的基础版本

**合并内容：** 新工程入口与必要约束、现有小屏时序、DDR 适配、双路 DVP、完整帧管理、视角选择、中文标题、按键消抖及 LED1～4。

内部顺序：

1. 复用已适配模块，在新工程内确认 HDMI 测试图可见；测试图保留为诊断源。
2. 单摄通过统一缓存显示，核对 RGB565 色序、首末行与帧发布。
3. 第二个摄像头通过另一个接收适配器加入，使用相同帧管理机制；验证后摄延长排线。
4. KEY5 先循环前/后两个有效视角；中文与实际来源一致。KEY1～4 驱动用户规定的意图灯，控制事件接口预留。

帧缓存从开始就支持四个来源及显示/网络两个读者，暂未接入的端口保持无效。建议三缓冲，读者持有期间禁止写端覆盖；无空槽时丢输入帧并计数。显示每帧读取哪个完整帧，在帧边界确定。

**交付验收：** 前后摄同时持续更新，可切换；画面颜色正确、不撕裂、不缺末行；遮挡一个镜头能确定对应来源；一侧断流不影响另一侧。首份板上版本包含实际摄像头画面，不只包含彩条和菜单。

### M2：增加 HDMI 左摄，一次接入基础处理和四宫格结构

**合并内容：** MS7200 接收、第三路缓存、统一缩放、四宫格合成、KEY5 扩展、KEY6 基础处理。

内部顺序：

1. HDMI-IN 先固定一种可验证的输入规格，转换到与摄像头一致的 RGB565 帧格式。
2. 显示模块支持单视角与固定四个窗口。M2 右摄尚未接入时，右摄格明确显示“待接入”，内部可用编号测试图验证坐标；不把它计作第四路真实输入。
3. 接入一份共享基础处理链：原图→灰度→去噪→二值→色彩空间→原图，KEY6 一次按下切换一次。
4. 中文放在处理链之后。四宫格滤波按窗口边界隔离；模式切换在帧边界生效，并重置必要的行缓存状态。

灰度/YCbCr 共用亮度计算，去噪先实现一种 3×3 滤波，不先堆多种近似算法；二值化共用亮度支路。Sobel 边缘可在之后需要道路候选时增加，不在此阶段承担道路语义判断。

**交付验收：** 前、后、左三路持续运行；单画面及四宫格结构正确；KEY6 的所有基础效果可复现；处理不改写原始彩色帧。此时 KEY5 可循环前/后/左/田字格，M3 接入右摄后形成完整五模式循环。

### M3：网口一次完成右摄输入、前摄输出和控制反馈

**合并内容：** 通用板网口1 RGMII、MAC/IP/UDP、右摄组帧、前摄分包、控制事件/心跳/ACK、电脑联调工具。

内部仍按依赖调通，但不拆成三个重复接线、重复集成的大版本：

1. 确认 PHY/RGMII 链路与 UDP 双向收发，固定视频/控制协议及字节序。
2. FPGA 从 FRONT 完整帧独立读取并上传，电脑接收显示。发送链先跑起来，后续也便于核对采集质量。
3. 电脑向 VIDEO_IN 发送右摄测试视频，FPGA 组完整帧写入第四个来源；显示模块直接使用 M2 已完成的第四格。
4. 将 KEY1～4 事件放入 CONTROL 通道，电脑返回允许/拒绝/未知及报警原因；FPGA 更新反馈。接收原图、发送右摄和控制模拟使用同一工具。
5. 三种业务同时运行，验证控制优先级、DDR 调度和网络断开恢复。

起步采用低负载规格排错，链路正确后再提高到目标帧率；不要每提高一个档位就交付一个新大版本。前摄最终目标仍为 1280×720@30 RGB565，约 442.368 Mb/s 像素载荷，实际结果以测试为准。

**交付验收：**

- 四路前/后/左/右同时更新；KEY5 循环前→后→左→右→田字格→前。
- FPGA 显示后摄或二值图，电脑仍收到前摄干净原彩色图。
- 右摄输入与前摄上传同时工作，按键/反馈保持有效，不因视频繁忙丢失控制状态。
- 网络丢包不发布不完整图；重复事件不重复执行；旧回包不能覆盖新请求；断网显示未知/通信失效。
- KEY1～4 与 LED1～4 保持用户映射，报警独立表达。

达到上述条件即发布 FPGA 基础版本。全景未完成，不强制让 KEY5 进入一个空白第六模式；全景通过后再加入循环。

### M4：香橙派联动道路理解，FPGA 显示结果与执行反馈

不再等待 FPGA 独立实现车道分类、道路类型或全景。香橙派沿用 M3 工具的协议和收帧代码，先用前摄原图完成真实识别闭环。

实施顺序：

1. 香橙派替代电脑接收器，确认原图显示和事件收发正常。
2. 接入交通灯与车道/线型识别，完成红停绿行、红灯行驶尝试告警、虚线变道、实线变道尝试告警。
3. 增加道路区域、斑马线、可见车道结构及道路类型；低置信度输出未知。行人/车辆/障碍物按场景逐项接入。
4. FPGA 按需要提供基础边缘、阈值、ROI 等特征，并承担结果线条/区域/中文叠加。是否增加特征传输，以实际算法收益为依据；首个闭环继续只传前摄原图。

结果回包与 M3 控制回包统一规划，至少关联来源、帧号、事件号、结果有效期和坐标系。FPGA 有限帧缓存需要保留图像或对延迟结果明确处理；不能将明显过期检测框画在当前移动物体上。

香橙派目前只收到前摄，因此其道路理解结果只作用于前摄画面或四宫格中的前摄子窗口；其他视角照常支持 FPGA 基础处理。不能把前摄检测线叠加到后、左、右视角。若以后确需其他视角复杂识别，再另行扩展上传策略。

**验收：** 基于真实画面与按键完成比赛操作，板上 LED/报警/中文反馈与有效识别结果一致；基础处理、视角切换不改变驾驶判断所用前摄来源。

### M5：四宫格稳定之后，单独开发全景

进入条件：M3 四路采集、完整帧、四宫格和负载测试通过，并具备可标定的四路视角数据。先检查实际前后左右视频是否有足够的几何关系与重叠，再选择全景投影方式。

实施顺序：离线标定和参考图→低分辨率定点映射→FPGA 四路重映射→接缝和亮度处理→性能优化。标定表可由电脑计算，运行时合成仍由 FPGA 完成。

**验收：** 重叠区域及地面几何有可量化的对齐效果，统计时间差、接缝和帧率。通过后 KEY5 扩展为前→后→左→右→田字格→全景→前。全景阶段独立记录资源与 DDR 带宽，不回退破坏已通过的基础版本。

## 4. 保留的接口约束

- **干净图与显示处理隔离：** DDR 原始帧只存统一彩色图，滤镜/文字/检测结果走显示支路；上传源固定 FRONT。
- **帧管理统一：** 每帧包含来源、帧号、尺寸、像素格式、采集时间和有效状态，所有读者遵守占用/释放机制。半帧不可发布。
- **DDR 按实际协议：** 沿用板卡已适配的 HMIC_S 及正确约束；它是简化 AXI，不能按完整标准 AXI 背压接口假设改写。
- **网络业务分开标识：** VIDEO_IN 为右摄输入、FRONT_RAW 为前摄上传、CONTROL 为双向控制；三种业务共享链路，独立类型/端口。
- **网络格式：** 首版发送已解码 RGB565，不在 FPGA 实现 H.264/RTSP。48 字节视频应用头继续作为草案，在 M3 一次固定。MTU1500 下像素分片最多 1424 字节，不依赖 IP 分片。
- **控制结果有效性：** 会话、事件、帧号及有效期都要校验；断流/失联进入未知状态，不能继续沿用旧的允许结论。
- **驾驶意图不变：** KEY1/2/3/4 为左/右/直/停，LED1/2/3/4 对应意图。KEY7 车道选择、LED5 报警等仍为此前建议，未变成用户已确认的新增定义。
- **测试文件输入：** 正常模式不改变固定方位映射。比赛文件如何注入前视算法，在 M4 作为显式测试模式定义，不能悄悄把右摄网络输入标成前摄。

## 5. 交付和验证安排

| 交付 | 核心板上演示 | 保留的关键检查 |
| --- | --- | --- |
| M1 | 双摄实景与前后切换 | 颜色、延长排线、帧完整性、读写互斥、断流隔离 |
| M2 | 三路显示、四宫格结构与基础效果 | HDMI 格式、窗口坐标、滤波边界、同步延迟 |
| M3 | 四路四宫格、前摄上传、按键回传 | 同时收发、丢包恢复、旧结果拒绝、控制优先级 |
| M4 | 真实视觉触发驾驶反馈 | 正负样本、帧关联、未知/过期、测试场景 |
| M5 | 标定全景与第六视图 | 几何误差、时间差、接缝、DDR 负载 |

对帧管理、DDR 适配及协议做针对性仿真；图像算法做软件参考比对。每次实际构建检查相关时序和资源，每个里程碑在预期组合负载下运行。完整四路基础版本做持续运行、反复切换和断流恢复测试；全景加入后再测新增负载。

交付写清“构建通过/待上板/用户已确认”，用户自行烧录。软件安装、IP 替换或自动烧录均不在本次计划调整范围内。

相较原路线，首份交付从“彩条和界面”提升到“双摄实景”，四宫格显示代码在网络接入前完成，网络三类业务一次集成；香橙派在 FPGA 基础版完成后即可进入真实算法联调。旧文档的硬件资料与带宽分析仍可参考，旧 S0～S14 不再作为串行排期。
