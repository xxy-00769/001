# FPGA_GSV1：FPGA 优先开发方案与阶段验收

> 已由 [FPGA优先开发方案V2](FPGA优先开发方案V2.md) 更新：用户已固定前/后/左/右输入，先四宫格再全景，道路理解与香橙派协同。本文保留为上一版设计记录；S0～S14 不再作为实施顺序，方位映射及独立 FPGA 道路理解等冲突内容以 V2 为准。

制定日期：2026-10-20。本文依据用户最新功能设想、既有交接及资料分析制定；这是开发方案，不是已实现功能清单。

**当前实施顺序：先完成 FPGA 独立采集、HDMI 显示、按键/LED、图像处理和网络接口，再接入香橙派的真实识别与驾驶判断。** 电脑可在前期充当网络图像源、接收器和控制回包模拟器。

本文更新了旧交接中的显示、全景和开发顺序：FPGA HDMI-OUT 是本次明确要求的显示出口；FPGA 承担当前画面的处理及后续全景重映射。香橙派负责前摄的复杂视觉及比赛驾驶逻辑。旧文档保留为历史资料，冲突处以用户本次要求和本文为准。

## 1. 功能拆分及实现边界

| 用户目标 | 实现安排 | 验收重点 |
| --- | --- | --- |
| 两路摄像头、一路 HDMI、一路网络输入 | 四个独立接收通道、独立时钟域和完整帧缓存 | 四路同时更新；切换显示不停止其他路采集 |
| KEY5 六种显示模式 | 四路单画面、田字格、标定后的全景 | 一次按下切换一次；显示帧边界生效；中文标题对应实际来源 |
| KEY6 处理当前画面 | 显示选择后使用共享处理链 | 不复制四套算法；原始帧缓存和前摄上传不受影响 |
| 灰度、去噪、二值化、色彩空间 | 定点流水线及少量行缓存 | 色序正确；原图/处理图同步；各模式有明确含义 |
| 道路边缘、道路/非道路 | 先实现指定视角、指定场景内的道路候选区域及边界 | 区分图像边缘和道路边界；输出置信度和未知状态 |
| 车道线、虚实线 | ROI 内提取候选线、拟合，再做连续性和多帧分析 | 左右边界分别分类；遮挡时不能把实线直接判成虚线 |
| 双向两/四车道、单向三车道等 | FPGA 在受限场景中尝试结构分类，后期由香橙派复杂感知补充 | 可见车道数不等于道路总车道数；证据不足显示“无法判断” |
| 斑马线 | ROI 内多条平行亮带、间距及透视一致性验证 | 排除普通虚线、护栏、阴影等干扰 |
| 只上传前摄原图 | 从固定的前视逻辑通道单独读完整帧，封装 UDP | KEY5/KEY6 不影响上传源、颜色或画面内容 |
| FPGA 按键与香橙派判断互联 | 本地请求状态、上报事件、接收判定、LED/OSD 反馈 | 请求、允许、实际模拟动作、告警分别记录；超时结果失效 |

这里的“原图”指完成接口解码、正确色序整理后的干净彩色图，不是传感器 Bayer RAW。建议首版统一 RGB565，避免为传输额外扩大到 RGB888。为降低负载而缩小上传图像时，应作为显式规格选项记录，不能仍称其为原分辨率上传。

### 1.1 四个输入接口不天然对应前、后、左、右

定义物理来源 `CAM0/CAM1/HDMI_RX/NET_RX`，再定义逻辑方位 `FRONT/REAR/LEFT/RIGHT`。映射由配置表决定，显示标签和前摄上传都查同一份表。

最初可用 CAM0→前、CAM1→后、HDMI→左、网络→右验证界面，但这只是功能测试映射。双目模组两个镜头通常朝向接近，贴上“前/后”标签不会改变实际视角。接入真实四方位视频后才能按实际布局标注。地图更新在帧边界提交，并使旧识别结果失效。

比赛文件模式可以把网络/HDMI 来源配置为逻辑前摄，让给定道路视频进入同一条采集、处理和上传路径。此时前摄上传继续跟随逻辑 FRONT，而不是跟随当前显示画面。

### 1.2 四宫格与真实全景分开验收

田字格只需缩放、摆放和来源管理。真实全景还需要镜头内外参、畸变校正、相邻视角重叠、投影映射、时间对应及接缝处理。

现有双目加两个任意视频源可以验证四路处理系统，不能据此保证得到真实 360° 环视。先用具有相机参数和时间对应关系的四路录制数据验证 FPGA 全景；实物最终环视还需满足镜头布局条件。若输入无相应几何关系，全景模式显示“待标定/输入条件不足”，不能用四张图横排冒充完成。

“只处理当前画面”适合共享滤波和特征计算；全景几何合成本身仍然必须访问四路输入，无法通过只读取单路完成。

### 1.3 道路检测的输出必须分层

Sobel 得到的是亮度边缘，路牌、车辆和树影也有边缘。需要 ROI、颜色、几何和时间约束后，才能称为道路或车道候选。

实虚线判断要观察沿车道方向的线段与间隙，并处理透视、遮挡和连续多帧。双向道路及高速路类型还需要中央分隔、行驶方向、道路标识或场景信息，单张前视图经常无法覆盖全部车道。

因此保留完整目标，但依次验收“候选图→拟合线→线型→可见车道结构→受限场景道路类型”。FPGA 不确定时输出 UNKNOWN；不能拿固定字幕或按键切换的标签充当视觉识别。对任意陌生道路的可靠语义判断，留给后续香橙派模型与融合结果。

## 2. 总体数据流

```text
CAM0 ─ 接收/色序 ─ 异步FIFO ─ 独立完整帧缓存 ─┐
CAM1 ─ 接收/色序 ─ 异步FIFO ─ 独立完整帧缓存 ─┤
HDMI ─ 解码/整理 ─ 异步FIFO ─ 独立完整帧缓存 ─┼─ DDR读调度
NET  ─ 解包/组帧 ─ 接收FIFO ─ 独立完整帧缓存 ─┘     │
                                                  ├─ FRONT干净帧 ─ 分包 ─ 网口TX ─ 香橙派
                                                  │
                                                  └─ KEY5选择/缩放/合成
                                                       │
                                                 共享处理链(KEY6)
                                                       │
                                                 中文/结果/告警OSD
                                                       │
                                                   HDMI-OUT

KEY1～4 ─ 消抖/事件 ─ 本地意图LED ─ 控制上报 ─ 香橙派驾驶判断
                                            判定回包 ─ FPGA校验/有效期 ─ 告警/状态/OSD
```

道路语义分析使用当前选中来源的合适分辨率 ROI，显示端再把结果映射到画面。不要先把单画面缩得很小再期望稳定识别细虚线；可从选中来源分出一条低分辨率分析支路，并与显示共用前级颜色/滤波结果。仍只运行一份当前视角分析器。

显示链是一组可选择的流水线，不能把处理后的像素写回原始缓存。所有模块传递并对齐 `frame_id/source_id/view_epoch/x/y/valid` 或等价元数据，保证颜色、坐标与叠加结果对应。

### 2.1 帧缓存与异步输入

- 每路建议三缓冲；帧槽状态至少包含空闲、写入、完整可读、被读者占用。采集写满且写事务完成后才发布。
- 显示和上传可以同时持有同一个完整帧，使用引用计数或读者占用位；读者未释放时写端不得覆盖。
- 没有空槽时丢弃新输入帧并计数，不能破坏正在显示或发送的帧。上传和显示优先消费最新完整帧，避免积压延迟。
- 四路各自有 PCLK/时钟，使用跨时钟 FIFO 和握手；不能直接把四路 VSYNC、数据或多位描述符接进同一时钟域。
- 四宫格可显示每路最新完整帧，但这不代表四路同步采集。全景需要按时间挑帧，并统计源间时间差。
- 第一版不能假设相机、HDMI、网络帧率一致。缺帧时允许重复上一完整帧；断流达到阈值后显示来源失效和帧龄。

现有 HMIC_S 是简化 AXI：用户口 256 bit、DDR 外部总线 32 bit。`axi_wusero_last` 是 IP 输出，且没有标准 AXI 的完整背压/响应组合。必须按实际 IP 指南封装，读命令发出前留够整个返回 burst 的 FIFO 空间。沿用旧缓存修复时，也应复用末拍间隙、末行及帧发布相关验证。

### 2.2 四宫格和全景的处理规则

单视角：基础滤波、ROI 和道路分析都作用于选中画面。

四宫格：灰度和颜色转换可以逐像素共享；3×3 滤波需要隔离四个子画面的边界，不能把接缝两侧当相邻像素。道路分析器依次复用处理各子画面，边界重置状态，并保存每个来源的结果；在资源/吞吐验证前允许降低分析刷新率，必须实报每路结果更新率。不能对整幅四宫格拟合一条“跨画面车道线”。

全景：基础处理可作用于合成图；前视车道算法直接套到俯视全景通常不成立，需要单独的 ROI/参数或算法。尚未适配的处理模式应显示“该模式暂不支持”，保留已完成的功能状态记录。

## 3. 按键、显示模式和反馈约定

### 3.1 KEY1～KEY6，保持用户映射

| 按键 | 功能 | 建议状态规则 |
| --- | --- | --- |
| KEY1 | 左转/左变道请求 | 本地立即更新左向意图，上报唯一事件；场景决定是转弯还是变道 |
| KEY2 | 右转/右变道请求 | 同上，方向为右 |
| KEY3 | 直行请求 | 也可用于停车后的行驶请求；红灯时尝试执行应触发判断/告警 |
| KEY4 | 停车请求 | 同时按键时优先；本地立即进入停车意图，再上报 |
| KEY5 | 显示视角循环 | 前→后→左→右→田字格→全景→前 |
| KEY6 | 当前显示画面的处理模式循环 | 原图→灰度→去噪→二值→色彩空间→道路候选→车道/线型→斑马线→原图 |

道路类型结果可在车道/线型模式中作为文字输出，不必为了显示一句结论再加一套视频链。必要时后续再拆独立模式。

色彩空间模式建议为 RGB→YCbCr，显示 Y 灰度或颜色分量的调试映射，OSD 写清当前分量。不能把 YCbCr 三个数直接当成 RGB 送出后，将异常颜色称为转换正确。

按键先同步，再消抖（初值建议 20 ms，实测调整），只产生按下边沿事件；长按不连发。KEY5/6 在显示帧开始处提交，网络事件不必等待显示帧边界。KEY1/2/3 同时触发且没有 KEY4 时，作为冲突请求忽略并记录，避免随代码优先级产生意外方向。

### 3.2 LED 与模拟驾驶状态分开

| 灯 | 用户规定/建议 | 含义 |
| --- | --- | --- |
| LED1 | 用户规定 | 左转/左变道意图 |
| LED2 | 用户规定 | 右转/右变道意图 |
| LED3 | 用户规定 | 直行意图 |
| LED4 | 用户规定 | 停车意图 |
| LED5 | 建议新增 | 违规告警；显示告警原因并保持到收到有效清除/新判定 |
| LED6 | 建议新增 | 控制通信与心跳正常 |
| LED7 | 建议新增 | 前摄图像有效 |
| LED8 | 建议新增 | 当前判定有效；灭灯表示未知/过期 |

LED1～4 建议互斥保持，复位为停车意图。LED1 亮只代表用户请求向左，不能代表识别允许向左。香橙派回包更新判定、模拟运动和告警，不能用一个任意远程 LED 位图覆盖掉意图语义。

至少维护：`current_lane`（当前车道）、`requested_action`（操作请求）、`motion_state`（模拟停车/行驶）、`verdict`（允许/拒绝/未知）、`alarm_reason`。画面可以显示“左变道请求 / 实线禁止 / 保持直行”，避免一个灯承担三个意思。

赛题还需要按键模拟当前左/直/右车道。建议把空闲 KEY7 用于车道循环，保持 KEY1～4 的操作含义；KEY8 先保留。前期也可由电脑配置当前车道，但最终按键演示需落实。此项是补足测试输入的建议，不是用户已指定的新按键定义。

### 3.3 后续香橙派的驾驶规则接口

- 路口模式：当前车道决定关注哪个方向灯。红灯自动停车；有效绿灯且没有手动停车保持时按当前车道模拟通行。
- KEY4 设置手动停车保持；有效的方向/直行请求解除该保持并发起执行尝试。红灯下仍提出行驶尝试，记录违规告警，模拟状态保持停车。
- 道路模式：左/右请求检查相应一侧车道边界；虚线且证据有效时允许变道，实线请求报警并保持原车道/直行，边界未知时输出未知。
- “报警”是对模拟强制操作的判定，不意味着 FPGA 真正控制车辆移动。本项目先实现按键、图像和 LED 的测试闭环。
- 场景类型可由上位机配置；普通左转请求不能在所有视频里一律解释成跨越左侧车道线。

FPGA 阶段用电脑回包验证这些字段与反馈。真正的红/绿灯和虚/实线结论，要到香橙派识别接入后才能验收，不能用定时灯或预设标签替代。

## 4. 分辨率、带宽与资源预算

### 4.1 初期规格

先保留现有 800×480 小屏的已知稳定输出时序，图像按比例缩放并留边；相机原始采集先沿用 1280×720@30 RGB565 配置。早期田字格可以在 640×360 内容区放四个 320×180 子画面。输出到其他显示器时另行验证 720p 标准模式，不把小屏专用时序当作通用显示器时序。

网络输入先用 640×360@15，再升到 30 fps，最后验证 720p30；所有目标均为工程建议，不是赛题官方固定门槛。显示 60 Hz 时，相机 30 fps 可以重复完整帧，不能因此宣称采集达到 60 fps。

### 4.2 RGB565 像素带宽

| 规格 | 像素数据速率 | 用途 |
| --- | ---: | --- |
| 单路 1280×720@30 | 55.296 MB/s = 442.368 Mb/s | 前摄上传目标 |
| 四路 1280×720@30 | 221.184 MB/s = 1769.472 Mb/s | 本地四路采集写入，不是单网口上传目标 |
| 单路 640×360@30 | 13.824 MB/s = 110.592 Mb/s | 低负载网络输入/联调 |
| 四路 640×360@30 | 55.296 MB/s = 442.368 Mb/s | 可选降规格的四路方案 |

单千兆口只上传一路前摄，有明显可行性；最终仍需测量有效吞吐。全双工允许 RX 视频和 TX 前摄各占一个方向，但每个方向仍只有 1 Gb/s 的链路上限。协议、包间隔和主机处理也有开销。

四路 720p RGB565 各三缓冲仅像素约 21.094 MiB，DDR 容量不是主要障碍。按四路各写一次 221.184 MB/s，加一路完整 720p30 显示读取 55.296 MB/s，再加一路上传 55.296 MB/s，示例合计为 331.776 MB/s。若四宫格实现成四路都全尺寸读一次再缩小，示例会上升到 497.664 MB/s；显示刷新率、缓存设计、映射表、插值和额外分析读取会继续改变需求。

DDR 理论引脚带宽约 3.2 GB/s，不可直接用来宣称这些组合一定能跑。应测量带仲裁和小块访问时的吞吐、FIFO 水位及超时。输出实时读应有时限保障，输入溢出与网口丢帧都有计数。

134 个 18 Kbit DRM 合计约 301.5 KiB，单帧 720p RGB565 约 1.758 MiB，完整帧必须放 DDR。DRM 留给异步 FIFO、行缓存、字库和小表。颜色转换、去噪、网络、DDR 与全景会共享逻辑和乘法资源，需逐阶段综合。

建议 LUT/DRM/APM 使用接近 70% 时先复核预算，接近 80% 时暂停增加功能并查时序/布局。这是项目内部提醒值，不是器件硬性边界或通过保证。运行时关掉算法可减切换功耗，却不会释放已综合的 LUT；“节省资源”的关键是共享实例、限制并行度和离线配置选项。

## 5. 网络接口先定义，再分别实现

使用当前通用板的 RTL8211E/RGMII 网口路径。首版用一个千兆口承载双向数据与控制，第二个口留作后续扩展，不引入专用网口底板的 QSGMII/HSST 例程。

| 通信通道 | 方向 | 内容 |
| --- | --- | --- |
| VIDEO_IN | 电脑/香橙派→FPGA | 网络输入的已解码 RGB565 图像 |
| FRONT_RAW | FPGA→电脑/香橙派 | FRONT 逻辑通道的完整干净帧 |
| CONTROL | 双向 | 按键事件、配置、判定、ACK、心跳 |

端口号、IP/MAC 和目标地址放配置中，S6 阶段固定实际值；不要假定原厂示例地址就是用户当前网络。网络视频是自定义像素协议，首版不做 H.264/H.265、RTSP 或普通视频文件解码。给定 MP4 等文件先由电脑/香橙派解码，再作为网络像素输入。

### 5.1 视频包草案

建议使用 48 字节应用头，包含：magic、版本、消息类型、头长、会话、流编号、像素格式、帧号、采集时间、宽高、帧内字节偏移、数据长度、标志、分片号、分片总数、可选整帧 CRC。字段位宽和偏移在 S6 固定成协议文档及软件共享常量；目前不是已实现接口。

普通 IPv4、MTU1500、无 IP 选项时，UDP 应用数据最多 1472 字节；减去 48 字节头，像素载荷最多 1424 字节。720p RGB565 一帧分 1295 包，30 fps 约 38850 包/秒。首版不依赖 IP 分片或 Jumbo Frame。

协议明确 RGB565 位段 `R[15:11]/G[10:5]/B[4:0]`；建议像素低字节先发、头部多字节整数使用网络字节序。软件按约定解包，不能只写“RGB565”而省略字节序。

网络输入检查会话、帧号、偏移、长度、包数和接收位图，支持识别重复包与乱序。只有完整且通过检查的帧才能发布；缺包超时丢整帧。初版实时图像不做重传，靠下一帧恢复；控制事件则独立 ACK/重试/去重。UDP 校验按 IPv4 规则及双方约定处理，可选帧 CRC 用于端到端核对。

### 5.2 控制回路

按键事件至少带 `session_id/event_id/action/current_lane/view_epoch/front_source_id/front_frame_id`；帧号不可用时置无效标志。`view_epoch` 用于标识界面配置；驾驶判断始终绑定 FRONT，不因显示后摄而改成判断后摄。

回包至少带 `session_id/event_id/result_seq/front_source_id/frame_id/verdict/motion_state/alarm_reason/valid_for_ms`。FPGA 拒绝旧会话、旧事件、过期帧以及前摄映射改变前的回包。新动作立即使旧动作判定失效；同事件的重复包不再次执行。

本机单调时间即可管理心跳与有效期；跨设备时间戳未同步时，不能直接相减声称测出了单向延迟。帧号、事件号、往返时间及录像可分别帮助验证链路。

建议初值：心跳周期 200 ms、超过 1 s 标记离线；判定有效期 300～500 ms，后续依实测调整。丢失心跳或图像时设判定 UNKNOWN、模拟停车，保留意图灯及“通信失效”原因；未知不等于违规，不可误触发闯红灯告警。控制优先级高于视频包，但已经发送的以太网帧不被中途抢占。

## 6. 逐阶段实现与验收

每阶段都交付源码、仿真/构建结果、资源与时序摘要、版本说明、可烧录文件（构建成功时）以及上板检查步骤。没有上板反馈的阶段只标“待实测”，不能根据仿真宣称板上通过。用户自行烧录。

### S0：建立新工程和基线清单

**实施：** 在新目录建立唯一 PDS 入口、顶层、源码清单、板级约束和时钟表；登记器件、DDR/IP 版本、各外设实际连接与已使用的引脚。按依赖提取稳定模块，不整包复制旧工程。V5.1 小屏时序作为参考，V5.2 的未验证状态单独记录。

**验收：** 新工程可从文档指定入口重建；无缺失源文件/错误器件；关键时钟与外部接口有约束，适用检查无未解释问题。生成第一个版本记录。

### S1：HDMI 输出、中文标题、按键和 LED

**实施：** 先不接摄像头，用彩条/灰阶验证 MS7210、800×480 输出和像素格式；加入小字库、KEY 消抖、KEY5/6 状态、KEY1～4 意图灯，建议状态灯单独参数化。

**验收：** 彩条、边框、首末行可见；中文“前摄/后摄/左摄/右摄/田字格/全景”可显示；按一次只变化一次、长按不连跳。此时模式切换只是界面验证，标题旁应标明测试图，不能说六路显示已完成。

### S2：一路摄像头→DDR→HDMI

**实施：** 接入 CAM0，复用已核对的 OV5640 RGB565 配置；验证字节拼接与红蓝顺序；建立单路三缓冲及显示读者占用机制。输出保持小屏规格，采集和显示独立。

**验收：** 实景颜色正确，无撕裂、末行丢失；帧号、宽高、帧率和丢帧可查；移动物体及断开/恢复摄像头时帧状态可恢复。先用已知色块确认，不只看“画面像是正常”。

### S3：在单路画面上完成 KEY6 基础处理

**实施顺序：** 原图旁路→定点灰度→RGB/YCbCr→3×3 均值或中值去噪→可配置阈值二值化。建议先均值，后按噪声类型加中值，不同时强塞两套。

**验收：** 每种模式有标题和可重复测试图；与软件参考输出核对取样像素/误差；图像与同步信号延迟匹配；切换发生在帧边界，恢复原图后干净缓存未改变。此阶段 KEY6 只循环已实现模式，高级项仍记待开发。

### S4：两路摄像头真正并行

**实施：** 两路独立接收、FIFO、帧槽和统计，共享 DDR 调度；实现 CAM0/CAM1 动态显示切换及干净帧读取接口。

**验收：** 两个镜头前放不同物体，两路帧号同时推进；显示一路不冻结另一路；一侧断流不拖垮另一侧。原厂 `CMOS1/CMOS2` 宏二选一只能参考驱动，不能当作并行完成。

### S5：HDMI-IN 成为第三个独立来源

**实施：** 配置 MS7200，先接固定 720p 视频源；确认输出总线格式、极性和像素时钟后再统一 RGB565；独立帧缓存接入调度。

**验收：** 摄像头两路和 HDMI 同时更新；HDMI 断接、恢复及不支持分辨率有明确状态；接收到的不是错误颜色或两像素错位。先支持一种输入模式，后续再扩分辨率。

### S6：先打通网口基础和控制收发

**实施：** 适配通用板网口1的 PHY/RGMII、MAC、ARP/IP/UDP；验证千兆协商、CRC、双向收发，加入控制包和收发统计。固定协议头、端口及字节序，提供电脑小工具。

**验收：** 可完成 UDP 双向数据核对、控制 ACK 和心跳；测出有效吞吐；重启、拔线后能恢复。RGMII 时钟相位、PHY 延时、输入输出时序和 CDC 有明确检查记录。原厂固定字符串发送成功不能算视频链路完成。

### S7：网络图像输入，形成第四路

**实施：** 电脑发送不同于摄像头/HDMI 的编号测试图或解码视频；FPGA 以包位图组完整帧，并写入 NET_RX 帧槽。从 640×360@15 提升到 30 fps，再试 720p30。

**验收：** 图像、帧号和源编号正确；丢包、重复、乱序、错误长度及发送器重启不产生花屏帧发布或越界写；缺包帧丢弃后下一完整帧恢复。四路现在都能独立持续采集。

### S8：KEY5 四路切换、中文和田字格

**实施：** 接入逻辑方位映射；四个单画面使用同一显示接口；四宫格先用最近邻缩放，验证后再考虑更好的缩放。OSD 在处理链末端叠加，子窗口显示来源和有效状态。

**验收：** 四个不同动态来源同时运行，KEY5 可循环、标签正确、没有跨帧混图；四宫格的每格都有对应更新；缺路时显示断流状态。全景入口暂显示待标定状态，S13 通过后才作为完整六模式验收。

把 S3 处理链接到这里，补齐子画面边界隔离与切换后的行缓存/算法状态重置。单视角处理时不启动其他路的道路分析。

### S9：只上传前摄的干净视频

**实施：** 给逻辑 FRONT 完整帧增加独立 DDR 读者、UDP 分包和速率调度；电脑接收并显示/保存。先低帧率排错，目标提升到单路 720p30 RGB565。

**验收：** FPGA 显示后摄、四宫格或二值图时，电脑仍得到前摄原彩色图，且没有中文/检测线；对测试图做收发像素一致性核对。上传慢时丢旧帧，不阻塞 HDMI 或覆盖未发送完的帧。网络输入和上传同时运行，报告两个方向的实测速率与丢帧。

### S10：按键→网络→模拟判定→板上反馈

**实施：** KEY1～4 上报动作事件；电脑模拟红/绿灯、实/虚线、未知和超时判定；FPGA 校验会话、事件及有效期，再更新告警/状态/OSD。建议 KEY7 补齐车道选择。

**验收：** 左右直停的请求灯正确；电脑允许/拒绝/未知反馈正确；重复包不重复执行；旧回包不能覆盖新动作；断网进入未知状态。红灯行驶尝试和实线变道尝试都有可见报警。这只是通信与反馈验收，视觉准确性仍待香橙派阶段。

S9/S10 在高级道路算法前完成，及早固定网络、DDR 和逻辑资源开销，减少后期因带宽/资源不足返工。

### S11：FPGA 道路候选与车道几何

**实施：** 用固定道路测试集做软件参考，依次实现 ROI→灰度/颜色阈值→滤波→边缘→候选点→行投影/窗口跟踪→简化直线或曲线拟合。先白天、单前视、清晰标线，再扩大场景。

**验收：** 同时提供原图、候选图和拟合叠加；有道路背景、阴影、车辆边缘的反例；缺少证据时不乱画。记录位置误差、误检和漏检，不能把一次演示截图当稳定识别。ROI 和系数按来源保存，切换视角不沿用上一视角的车道结果。

### S12：实虚线、斑马线及道路结构

**实施：** 沿拟合边界分析占有率、线段/间隙长度与多帧稳定性，左右分别给出实线/虚线/未知；斑马线独立验证平行亮带。再估计可见车道边界、车道数、中央分隔与方向线索，尝试受限场景类型分类。

**验收：** 实线、虚线、遮挡、弯道、斑马线、无标线各有样本；换一组未参与调参的视频再测试。道路类型输出带“可见/推测/未知”及置信度，不能把两条线等同双向两车道。四宫格按来源分别分析，报告每路更新率；全景的道路模式另行适配。

如果受限资源或效果不足，先保留可验证的候选与结构输出，记录未通过项，再做算法调整或由香橙派提供补充判断；不把未通过项写成已完成，也不从需求列表删除。

### S13：真实全景，完成 KEY5 第六模式

**实施顺序：** 准备具有真实视角关系的四路数据→离线标定与浮点参考→生成定点重映射表→FPGA 单路映射→四路拼接→重叠区亮度/接缝处理→可选双线性插值。首版建议低分辨率、最近邻，逐项测 DDR 随机读与映射表带宽。

离线在电脑上计算标定参数不改变运行时全景在 FPGA 完成的分工。映射坐标和融合权重优先放 DDR，小缓存加速连续读取，不能假定片上 RAM 能容纳全表。

**验收：** 静态地面线条和重叠区域对齐，移动物体的不同步/重影可量化；记录源间时间差、标定误差、接缝、刷新率、资源和 DDR 负载。没有环视硬件时先交付已标定录制数据上的运行结果，实物环视保留独立待验项。

### S14：FPGA 集成验收和可回退发布

**实施：** 全部来源、显示、共享处理、上传和控制同时运行；长时间测试、反复切换、断开任一路、停止发送器及网络重连。全景/算法重负载下观察 FIFO 水位、丢帧和 HDMI 欠载。

**验收：** 输出一份“通过/待实测/未通过”矩阵、资源和时序报告、各来源实际帧率、结果更新率、视频/控制延迟、丢帧/恢复统计。建议至少连续运行 30 分钟并覆盖反复切换；这是项目测试目标。保留最近通过版构建及源码清单，才进入香橙派真实算法接入。

## 8. FPGA 完成后的香橙派接入顺序

1. 用香橙派接替电脑接收器，先显示并保存前摄原图，沿用已经验证的协议。
2. 部署红绿灯和车道/线型识别，保留帧号、结果时间和置信度；把真实判定接入已验证的事件回路。
3. 完成当前车道选择、红停绿行、红灯强行驶告警、虚线变道、实线变道告警。
4. 加入行人、车辆、障碍物及 1～2 个具体场景，按数据集验证效果。
5. 补齐给定 U 盘视频的解码/输入、导航场景及演示材料。需要在 FPGA HDMI 显示 ARM 检测框时，再增加绑定前摄帧号的结果叠加协议；这不是首个 FPGA 版本的依赖。

用户选择的“仅前摄上传”可以覆盖本次复杂算法主链路；四路本地采集与显示，不能直接等同赛题高阶的四路低延迟传输和多路 ARM 识别全部完成。后续若争取该部分，再单独安排四路降规格传输与多路推理，不擅自扩大首期网络目标。
