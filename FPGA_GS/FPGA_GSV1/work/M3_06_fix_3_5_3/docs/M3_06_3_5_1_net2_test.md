# M3-06 3.5.1 网口2被动诊断候选

本版不是“已恢复收发”的声明。现场根因尚未确认；没有证据支持修改采样边沿、PHY寄存器、ready门控或CRC。本次只补实际可读状态和缺失的生产链路定向验证，等待一次板测定位首个失败环节。

## 唯一基线与范围

基线是 release/FPGA_GSV1_M3_06_3_5/source。原包294个文件SHA256全部匹配，构建147个冻结输入与发布源码完全一致；原位流SHA256为760A6077FAB0AC19E4351DC51E1185F4C1FA6D5CAEC930BFEC539460A3FEB332。

根目录3.4 WIP没有用于本次构建，也没有覆盖或删除。摄像头、HDMI、滤镜、DDR、网口1收发实现及协议/端点配置未变。网口2ready/复位/CRC/MDIO事务和PHY配置也没有改变。

诊断通过板载CP2102 USB串口输出，115200、8数据位、无校验、1停止位、无流控，每秒一行。TX是R9，引脚依据板卡官方04_uart_test/uart_test.fdc；不使用KEY或LED，不需要香橙派安装依赖。

## 最短验收

1. 用户自行加载本版唯一sbit，网线沿用原连接。网口2是靠HDMI-OUT的一口。不要改IP、端口、路由、算法或分辨率。
2. 在香橙派只删除定位时添加的静态邻居：

   ```sh
   sudo ip neigh del 192.168.60.2 dev eth0
   ```

   如果提示不存在，继续。保持原LIVE_FRONT运行（绑定192.168.60.1:50000，对端192.168.60.2:50000）。等待5秒：

   ```sh
   ip neigh show 192.168.60.2 dev eth0
   ip -s link show dev eth0
   ```

   正常：邻居自动得到02:00:47:53:56:32，状态可能REACHABLE/STALE/DELAY，不能是INCOMPLETE/FAILED/PERMANENT；RX递增。不要重新加入静态MAC，不以ping判定。
3. Web诊断应online=true，收到板端心跳、视频分片、完整CAM0彩色原图，processed或完整帧数持续增加。保持10秒，记录实际接收fps；5fps是原上传请求值，本版没有板测性能数据。遮挡前摄应改变Web画面。切换显示/滤镜不应改变上传来源和原始颜色。
4. 闭环恢复后，只抽查一次网口1原15fps右摄、1080p60显示及KEY5/KEY6切换。KEY/RESULT闭环留到前摄恢复之后。

## 若仍失败：一次采够分阶段证据

用数据线把板载USB转串口Type-C接电脑（不是只供电线）。这是读取诊断所需新增连接。已有CP2102驱动时无需安装软件；本任务不会安装驱动。如果系统没有COM口，只回传“未出现CP2102 COM口”，不要反复改网络。

电脑PowerShell列出串口：

```powershell
[IO.Ports.SerialPort]::GetPortNames()
```

选择板卡CP2102对应的实际COM号，关闭占用该串口的软件。进入本发布包source目录，执行（COM7替换成实际值）：

```powershell
& ./tools/m3/read_net2_diag.ps1 -Port COM7 -Seconds 15 -Output net2_diag.txt
```

保持LIVE_FRONT和网线不动。脚本读取15秒后自动关闭串口，保存原始行并解码首末快照。不打开网络socket，不改配置。也可用已有串口终端按115200 8N1无流控保存15秒日志。

失败时只回传：

- 实际烧录文件名和SHA256；网线确实在靠HDMI-OUT的网口2。
- net2_diag.txt（15秒原始日志）及上述一次邻居/eth0统计。
- Web诊断一张截图，包含online、heartbeat、分片、完整帧和实际fps。

不需要重复分辨率、算法、Wi-Fi或全部历史功能测试。

## 串口字段与故障区分

每行 `N2 351` 后22个8位十六进制字，字段从0编号。一次发送前锁存整行；不同域使用握手快照，域间观察可能差数个时钟，不用于逐拍对齐。

| 字号 | 内容 |
|---|---|
| 0 | 高16位PHY ID1，低16位ID2；期望001C/C91x |
| 1 | 高16位延时寄存器核验值（应包含3800），低16位MDIO无ACK累计 |
| 2 | 高16位ID不匹配累计，低16位延时回读失败累计 |
| 3 | 高16位PHY reg17；低16位：bit15配置完成、14 ready、13 RX时钟活动、11:8管理步骤、4:0扫描地址 |
| 4 | ready门控之前的RX_CTL报文包络累计；仅指示输入活动，不证明MAC正确收包 |
| 5 | 接收桥输出RX有效包络累计 |
| 6 | MAC通过CRC/长度检查后发布的帧累计 |
| 7 | MAC CRC/长度/RX_ER错误（原MAC计数；队列重置会清零） |
| 8 | MAC包槽满（原MAC计数；队列重置会清零） |
| 9 | MAC TX有效包络累计；不能单独证明PHY线上成功发送 |
| 10 | MAC ready下降的队列复位次数 |
| 11 | 接收桥有效字节累计 |
| 12、13 | core扫描包数、协议拒绝包数 |
| 14 | 高16位ARP接受次数，低16位HELLO接受次数 |
| 15 | 会话ID |
| 16、17 | 上传完整帧、上传中止累计（原上传器输出） |
| 18、19 | core向MAC请求发送次数、MAC完成握手次数 |
| 20 | bit4 online、3 core_ready、2 MAC_ready、1 TX请求toggle、0 TX完成toggle |
| 21 | bit2 PHY reset已释放、1 core_ready、0 MAC_ready，已同步到串口系统时钟 |

MDIO扫描未命中地址产生无ACK是正常的；看最终ID、地址、ready及15秒增量，不能凭一个累计值认定故障。PHY状态应满足千兆、全双工、协商完成、链路建立，不能只看carrier。各计数32位自然回绕，ARP/HELLO和PHY诊断计数16位自然回绕。全局复位清零，单独队列复位保留诊断累计；7/8除外。

| 观测 | 下一处定位 |
|---|---|
| 无串口行 | 先确认COM号/USB数据连接/是否加载本版，不能由此判定网口PHY坏 |
| ID/延时核验未完成或ready=0 | MDIO/PHY管理/时钟或状态门控；原始RX活动仍可观察 |
| ready正常，4不增 | PHY至FPGA RX_CTL引脚前的输入链路或物理端口 |
| 4增、5不增 | IDES/接收桥/其复位释放 |
| 5增、6不增、7增 | 字节/控制/CRC/帧长链；不绕过CRC |
| 6增、12不增 | 包槽CDC或队列/core复位 |
| 12增、ARP/HELLO不增 | 参数匹配或协议拒绝，结合13和实际邻居/会话 |
| ARP/HELLO增，18不增 | TX调度 |
| 18增，19/9不增 | MAC发送或ready复位 |
| 9/19增，香橙派RX仍为0 | FPGA TX至PHY/引脚时序路径，需进一步电气证据 |
| 心跳正常、上传16不增 | 再查前摄独立上传读者/HELLO上传请求；不提前归咎组帧 |

## 实际验证的界限

新仿真覆盖生产m3_network的PHY管理、nr/queue复位、IDES4字节桥、真实DRM MAC、core，以及TXC/TXD引脚重组和FCS校验；输入ARP、HELLO、坏FCS、ready下降期间输入、恢复后的第二次ARP/HELLO。没有替换ready为1。仅缩短PHY等待/轮询和MDIO周期；测试将复位计数器预置到释放前16拍以缩短84ms启动，释放和后续门控仍是生产逻辑。板上时钟/计时参数未改。

时钟插入使用固定模型，未模拟PCB、真实PHY电气特性和PAP_IO_IN_DELAY物理延迟；这仍不能证明板上兼容。串口单测验证整行207字符的8N1编码及22字字段顺序。摄像头、滤镜、完整视频/算法回归没有重跑。
