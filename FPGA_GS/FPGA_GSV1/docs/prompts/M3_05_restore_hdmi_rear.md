# M3-05 3.4：恢复HDMI左摄、修复后摄新增绿点

用户最新要求优先：原来功能正常，现在HDMI左摄失效、后摄新增很多边缘绿点。让开发AI自查并实际修复，停止扩功能，不重复没必要或已通过且未受影响的验证。项目`E:/zhoumian/FPGA/FPGA_GS/FPGA_GSV1`，遵守开发指挥约定，实际修改构建交付，不只给诊断计划。

## 本轮唯一目标

恢复原有HDMI左摄和后摄画质，保住右摄15fps及1080p60输出。暂停30fps优化、网口2、M4和其他新功能。

事实：用户确认15fps流畅，截图短窗发送14.37、板端发布14.27、显示新帧14.31、前摄接收4.98fps，作为已获实物反馈的性能基线保留；不要求为了形式再重复同一轮70秒测试。HDMI左摄黑屏提示“无信号/需720p60”，用户已明确确认电脑到板HDMI-IN活动信号就是1280×720、60/59.94Hz，原来可用。不得把问题推给用户改分辨率、换屏、换线。后摄边缘绿点是用户新报回归，不得当成正常噪声搪塞。

指挥侧已核对3.2/3.3发布源码：hdmi_input、hdmi_rx_config、ms7200_ctl、video_capture_status、capture_pipe、pll_mpi7001内容一致，顶层和constraints无差异。这不证明硬件没回归；从共享路径、帧地址/时钟/复位/实际IO影响排查，不凭猜测重写HDMI配置。需要时再对比更早用户确认正常的发布包。

## 自查后直接修复

1. 以已冻结发布源码为依据对比近期实际变更，保留用户工作区，检查右摄三槽扩展后的所有帧地址/槽号/来源位、仲裁路由、burst边界及等待/释放，尤其与后摄和HDMI来源是否互相覆盖、误清有效标志或被饿死。发现不必要的改动可局部撤回，不能把整个版本退回到网口卡顿状态。
2. HDMI按MS7200配置完成→输入时钟/同步/DE→尺寸/帧率判定→capture_pipe→完整帧发布→显示读逐段定位，只加能定位首个失败环节的少量状态。不能把所有失败统一解释成“需720p60”；如需诊断，明确区分初始化未完成、时序判定、采集/DDR未发布、读欠载。不要为此建立庞大新监控框架。
3. 核对HDMI输入及双摄已有时钟、复位释放、CDC和外部采样约束/IO寄存器；网络资源/布线变化可能影响未完整签核的IO，不能因源码不变就排除。没有证据不盲改摄像头/HDMI采样边沿、PLL相位或接收寄存器。
4. 后摄绿点检查原图路径的RGB565打包/字节顺序、DDR地址/数据拍、跨行边界、滤镜/增益流水对齐及显示读欠载；关注固定边缘与运动边缘是否相关。按实际证据修改。不能用裁边、涂黑、加重去噪/锐化/调曝光或降分辨率掩盖数据问题；不默认归咎延长排线，也不让用户反复换线代替自查。
5. 保持HDMI-IN原有720p60/59.94契约、HDMI-OUT标准1080p60、KEY5/6、中文、LED/停车优先、前摄干净原图上传、文件视频和已流畅15fps，不擅自改变其含义与参数。

## 检查边界：修哪里，验哪里

先按生产代码自查，已有定向证据能定位就直接修，不陷入长时间搭夹具或算法调参。仅运行能证明本次修复的定向检查；未改动且依赖未受影响的滤镜定点穷举、网络协议全量、反复软件回环等不重跑。若涉及共享DDR/地址/同步，保留能证明四来源隔离/帧保护及像素对齐的一组最小组合检查，因为它直接关系本次回归。

RTL修改后的综合、布局布线、真实约束STA和新位流构建是必要交付条件，不能省掉或放宽约束。通过后即交付3.4；不为增加报告数字重复测试。某症状只能板上确认时如实标待测，给一轮最短操作，不盲发多个版本让用户来回试。连续排查无新证据应调整假设，不重复相同流程。
