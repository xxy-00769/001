## 3. 最终固定的 FPGA 与香橙派分工

核心原则：

> **FPGA 把画面采好、整理好、做基础处理；香橙派理解画面、判断道路情况、生成驾驶提醒。**

这一分工覆盖早期对话中把最终车道识别、驾驶决策和显示混在 FPGA 上的部分建议。旧代码里的检测和规则模块不因此自动进入新版本。

### 3.1 职责表

| 功能 | FPGA：MES50HP | 香橙派 5 |
| --- | --- | --- |
| 双目摄像头、HDMI 输入 | 配置接口、接收像素、检测断流 | 不重复承担 FPGA 端底层采集 |
| 外部网络图像输入 | 接收数据包、组装完整图像 | 文件模式下发送解码后的图像 |
| 多路图像管理 | 通道号、帧号、采集时间记录 | 接收、对应各路画面 |
| 图像缓存 | DDR、完整帧管理，避免串帧、覆盖和撕裂 | 接收、识别和显示队列 |
| 颜色格式整理 | 转成约定的彩色格式 | 模型要求的最终转换和归一化 |
| 裁剪、缩小 | 负责，减少传输和后续计算量 | 模型所需的最后尺寸适配 |
| 灰度、简单滤波 | 按需启用 | 使用处理结果 |
| 边缘、颜色或亮度阈值 | 提取基础候选特征 | 理解特征的道路含义 |
| 车道位置、曲线拟合 | 提供道路区域和候选特征 | 最终检测与拟合 |
| 实线、虚线 | 提供候选线条、边缘 | 最终判断 |
| 斑马线、道路边缘、可行驶区域 | 基础处理图像 | 检测与理解 |
| 红绿灯、行人、车辆、障碍物 | 保留可用彩色图像 | 最终识别 |
| 多帧跟踪、结果稳定 | 连续帧和帧号 | 跟踪、置信度、结果稳定 |
| 驾驶操作判断、违规告警 | 上报按键、执行 LED 命令 | 决策与提醒 |
| 四路全景 | 独立图像和时间记录 | 标定、对齐、视角变换和融合 |
| 检测框、文字、最终 HDMI | 可选调试显示 | 正常系统显示 |

### 3.2 FPGA 两条图像路径

```text
摄像头 / HDMI / 网络图像
              ↓
      接收、编号、完整性检查
              ↓
         图像缓存与分流
          ┌───┴─────────┐
          ↓             ↓
     彩色图像路径     道路特征路径
     格式整理         裁剪道路区域
     按需要缩小       灰度 / 颜色筛选
          ↓           简单滤波
          │           边缘提取
          └─────┬───────┘
                ↓
         传输到香橙派
```

**彩色图像是主数据，特征图是辅助数据。**

- 不能把整个系统唯一的输出强制变成灰度或边缘图，红绿灯和目标识别需要可用彩色信息。
- 特征图应与原始帧关联，并标明裁剪位置和缩放关系。
- 不要求每一种特征都长期上传；先证明对识别有收益，再决定是否占用传输带宽。
- 算法候选涂色、文字、边界线和 HUD 不应覆盖供香橙派使用的干净彩色主图。
- 本地调试显示可以切换特征效果，但不能把显示模式变化和正常彩色上传意外绑定。

### 3.3 变道闭环示例

```text
FPGA 采集道路图像，基础处理并发送
                ↓
香橙派检测右侧车道线，判断为实线
                ↓
FPGA 上报一次“右变道”按键事件
                ↓
香橙派结合识别结果和事件判断风险，显示提醒
                ↓
FPGA 收到告警命令，执行 LED 输出
```

FPGA 不负责最终判断“这次变道是否合法”；香橙派不代替 FPGA 采集接口、DDR 与输入完整性管理。

## 4. 用户指定的功能范围与步骤

### 4.1 FPGA 首版必须完成

1. 一路视频采集，再逐步扩展双路和四路。
2. 通道号、帧号、图像规格、采集时间记录。
3. DDR 完整帧缓存。
4. 颜色格式整理。
5. 可配置裁剪、缩小。
6. 视频传输和配置接收。
7. 按键事件上报、LED 控制。
8. 运行统计、断流检测与恢复。

这里描述的是首版主线及扩展方向，**不要为了同时完成四路而让第一条单路链路迟迟不能验收**。单路、双路、四路应分别标记状态。

### 4.2 FPGA 第二阶段增加

- 灰度转换。
- 一种简单滤波，例如均值或高斯滤波。
- Sobel 边缘提取。
- 可配置颜色或亮度阈值筛选。

要求支持开关和效果对比。旧工程的中值滤波可以作为参考，但不代表新版本已经指定必须采用中值滤波。

**亮度增强不是首版强制主功能。** 旧 V5.2 的显示提亮只属于显示端调整；新架构是否加入图像增强，应根据实际收益决定，不能默认改变上传给模型的图像。

### 4.3 香橙派三个部分

| 部分 | 输入 | 输出 |
| --- | --- | --- |
| 道路识别 | 彩色图像、可选特征 | 车道、线型、红绿灯、行人等 |
| 驾驶判断 | 识别结果、按键请求、结果有效时间 | 停车、允许操作、风险提醒或无法判断 |
| 显示与控制 | 图像、识别及判断结果 | HDMI、日志、发往 FPGA 的 LED 命令 |

识别无效、超时或者失联时，需要有“无法判断”状态，不能继续把旧结果当作当前道路结论。

### 4.4 用户给定的落地顺序

1. **彩色主链路：**一路输入 → FPGA 缓存 → 香橙派显示。
2. **FPGA 裁剪、缩小：**保证图像正确，保留坐标变换关系。
3. **香橙派单路识别与判断：**先做红绿灯、车道线和实虚线。
4. **FPGA 基础特征：**加入滤波、边缘等，比较识别效果和处理时间；无收益的模块关闭。
5. **双路、四路：**验证每路独立、带宽和断流恢复。
6. **进一步场景：**斑马线、道路边缘、行人等，最后进行全景融合。

过去曾讨论先完成更多 FPGA 本地功能再联网；最新明确的顺序以上述链路为主。并不要求现在物理接上香橙派才能编写和检查每一个基础模块，但接口、数据格式和目标带宽应尽早明确，不能等 FPGA 所有功能写完才设计板间通信。

## 5. 多路输入问题的对话结论

### 5.1 双目接口与四颗摄像头

本对话反复讨论过：MES50HP 目前一个双目插槽，能否四路、能否自制四摄板、能否用两块 FPGA。

整理后的结论：

- 一个双目模组可提供左右两幅图像，但工程中有两个配置或采集实例，不代表后级已经双路并行工作。
- 旧主工程以宏选择一路进入处理和缓存。不能据此宣称双目并行已完成。
- 自制四摄板并非简单把插槽“分成四个”。需要核对引脚、电气、时钟和总带宽；若采用主动汇聚，还需额外桥接逻辑、缓存和协议。
- 两块 FPGA 各采两路是可评估的扩展方法，但仍需验证每板双路采集、上传带宽和跨板时间关系。
- 本对话没有拿到“比赛限制最多一块 FPGA”的依据，也没有得到官方对双板方案的专门确认。不要把“未发现限制”写成官方已批准。
- 第二块 FPGA 不是当前默认必需采购项。

### 5.2 混合四路候选

讨论过的单板候选输入为：

```text
双目左图  → 通道 0
双目右图  → 通道 1
HDMI-IN   → 通道 2
网络像素  → 通道 3
```

今年赛题写的是至少四路视频流并行采集、模拟前后左右，并未在这句话中限定必须四颗直连摄像头。混合输入可以作为作品的技术路线，但要明确：

- 必须是独立的视频来源，不把 HDMI 同一路复制两份充数。
- 网口必须真正接收图像像素并在 FPGA 内组帧；网口输入字符不能算视频流。
- 网络 H.264/H.265/RTSP 不能直接当作 RGB565 像素输入，解码通常在电脑或香橙派完成。
- 四路拼成四宫格不等于几何意义上的汽车环视。
- 实际全景融合需要合适的视角、标定、时间对应和重叠区域。
- 模拟四路是否满足全部比赛高阶评分，不能由工程方案自行承诺。

用户还提过视频中的光口输入。光口只是传输载体，仍需具体收发器、链路协议、像素格式与接收工程；香橙派也不能通过普通线缆自动接收 FPGA 的 HSST 数据。

### 5.3 双板方法的比较

| 方法 | 做法 | 本项目中的位置 |
| --- | --- | --- |
| 各采集板上传 ARM | 每块 FPGA 独立采集，香橙派汇总 | 若未来需要双板，值得优先比较 |
| FPGA A 转发 FPGA B | B 接收 A 的图像并合并本地输入，再上传 | 增加一层缓存、同步、转发与瓶颈 |
| 一块采集、一块计算 | 图像板与计算板分工，再返回结果 | 不是当前“复杂算法放香橙派”的默认路线 |
| 高速光口互连 | 高速点对点数据链 | 需求和性能确有必要时再评估 |

两块板的帧号相同不等于同步曝光；跨板时间戳如果没有共同时间基准，也不能直接相减作为真实采集时间差。

## 6. 板间通信、带宽与显示的最终口径

### 6.1 通信方式

用户明确说过：**没有要求必须网口，按实际合适的接口选择。**

已有讨论建议首版优先验证千兆以太网 UDP，主要因为便于接电脑调试和后续迁移香橙派，并非用户硬性限定。

| 方式 | 对话结论 |
| --- | --- |
| 千兆以太网 | 当前首选验证路线，普通合格 Cat5e/Cat6 网线；仍需实现 FPGA PHY/MAC/UDP 和图像协议 |
| UART | 适合日志、小量控制；不作为正常视频主通道 |
| PCIe | 潜在高带宽路线，但板型、物理接口、内核和 DMA 驱动都需要适配 |
| USB3 视频采集 | 可作为另行评估路线，需要合适的采集桥和驱动；不能把开发板 USB 口想当然视为视频设备 |
| 光口 / GPIO 扩展 | 需要额外链路、接收硬件与协议，不因为接口存在就自动可用 |

有两个网口也不代表工程已经支持两个网口。新工程应只依据实际驱动和验收的端口做功能声明。

### 6.2 双向数据内容

| 方向 | 内容 |
| --- | --- |
| FPGA → 香橙派 | 彩色主图、可选特征、通道号、帧号、尺寸、格式、采集时间 |
| FPGA → 香橙派 | 按键事件、输入状态、丢帧和错误统计 |
| 香橙派 → FPGA | ROI、缩小尺寸、处理开关、发送帧率等配置 |
| 香橙派 → FPGA | LED、告警状态、心跳 |
| 香橙派 → FPGA | 文件输入模式下，解码后送入 FPGA 的图像 |

协议需要处理版本、运行会话、帧身份、分片、有效长度、丢包、重复、乱序、超时和重启恢复。历史结果编码和软件解析不能直接等同于这个完整协议。

采集时间要说明来自哪个时钟、记录在哪个边界；在没有时钟对应测量时，不把 FPGA 时间戳直接与 Linux 时间相减作为端到端延迟。

### 6.3 带宽算术

以下只有未压缩像素载荷，不包含网络包头、特征图和其他开销，也不是实测值。

| 规格 | 单方向像素载荷 |
| --- | --- |
| 单路 1280×720 / RGB565 / 30fps | 442.368 Mb/s |
| 双路同规格 | 884.736 Mb/s |
| 四路同规格 | 1769.472 Mb/s，超过单千兆 |
| 单路 640×360 / RGB565 / 30fps | 110.592 Mb/s |
| 四路 640×360 / RGB565 / 30fps | 442.368 Mb/s |
| 四路 640×360 / RGB565 / 15fps | 221.184 Mb/s |

只上传前摄高质量图像、其他视角较低频率，是减小带宽的一种办法；但不能由此说带宽已经无须考虑。若要香橙派完成四路全景，它仍需取得四路图像。

千兆全双工是收、发方向各有上限，不能把单方向理解成 2Gb/s。两块 FPGA 经交换机汇总，也不能绕过香橙派单个千兆接收口的总上限。

### 6.4 显示职责的变化

早期讨论过“FPGA HDMI 输出四路合成，香橙派只做前摄识别”；也讨论过由 FPGA 叠加回传的检测框。

后来用户选择：**香橙派输出最终正常画面，FPGA HDMI 保留可选调试显示。**

因此新版本不应把以下功能当作默认必做项：

- 将香橙派识别框回传给 FPGA 绘制。
- 强制由 FPGA HDMI 承担最终 ADAS 界面。
- 让 FPGA 做最终全景标定融合。

无 AI 叠加预览和识别画面可以共用接收服务。以后增加独立原视频脚本时，也应共享完整帧来源，避免两个脚本争抢同一 UDP 端口；“无叠加预览”不代表能还原 FPGA 已丢失的分辨率和颜色信息。

## 7. 2023 与今年赛题的对比结论

两份赛题原件已经进入工作空间。今年赛题为 2026 版，ADAS 内容在 PDF 物理第 14–16 页。

| 项目 | 2023 年 | 2026 年 |
| --- | --- | --- |
| 相关视频方向 | 赛题一：多媒体视频处理魔盒 | 选题三：高级辅助驾驶系统 |
| 主要目标 | 拼接、缩放、旋转、去噪、融合、叠加和显示 | FPGA+ARM 协同、道路识别、场景判断与提醒 |
| 输入说明 | 双目摄像头和 HDMI；以太网为叠加字符输入 | HDMI、摄像头或其他图像输入；高阶至少四路视频流 |

| AI 与处理器 | 不能直接套用为今年要求 | MCU 端轻量模型、多路识别和自主规划等 |

关键纠正：**2023 年第三题是 RISC-V 游戏机，不是 ADAS。** 可以借鉴当年的视频处理模块，不能说今年赛题只是换了名字。

今年官方原文同时包含：

- 处理器性能不高于 RK3568 的约定；用户已经选择继续使用 RK3588S 制作作品。
- FPGA 图像处理、软硬协同通信、道路感知及完整演示要求。
- 四路视频并行采集与低延迟传输为高阶任务。
- 现场可能通过 U 盘提供十字路口、变道、红绿灯、导航等视频或图片。
- 完整源码、技术文档、资源与性能报告、实物，以及 1080P、3 分钟以内演示视频等材料。

本对话固定的是作品的工程分工，不应在后续文档中把“基础预处理已完成”直接写成所有比赛道路感知要求已经满足。

## 9. 旧工程已经有什么、哪些不进入新主线

### 9.1 有复用价值的内容

| 资产 | 历史情况 | 新版本的定位 |
| --- | --- | --- |
| OV5640 配置、DVP 采集 | 旧主线已有 CMOS1 单路 | 按依赖提取，重新确认接口和色序 |
| RGB565 整理 | 旧顶层有红蓝位段调整 | 明确内部格式与字节序，用纯色验证 |
| DDR 与缓存 | 有持续开发和定向缺陷修复记录 | 重点借鉴完整帧发布、首末行和恢复 |
| 帧所有权 | 旧 V3 有写入/发布/读取保护记录 | 避免读写同一活动帧、覆盖和撕裂 |
| 采集状态与恢复 | 旧 V2 有元数据、断流和局部恢复 | 根据新结构复用，不只保留显示效果 |
| KEY8 消抖和帧边界切换 | 旧 V4 有六档切换 | 可以参考事件机制；不强制沿用全部六档 |
| 灰度、滤波、Sobel、阈值 | 旧工程有实现和部分测试 | 第二阶段的候选模块，不整块照搬 img_proc |
| HDMI 与 MPI7001 时序 | 已有显示适配和用户反馈 | 仅作为调试出口和兼容参数参考 |
| CRC、超时、参考模型、测试台 | 各阶段已有资产 | 保留方法，选择与新接口一致的用例 |
| 主机诊断协议工具 | S5 应用层和软件回环记录 | 不等于实体网口已打通 |

历史 DDR 记录中特别有价值的问题：

1. 读返回最后一拍前出现间隙时，完成握手曾有异常；后续已有局部修复记录。
2. 旧读缓存曾出现末行缺失问题；后续有读行计数修复和完整帧验证记录。
3. 缓存有图像不代表帧已经完整，只有完整提交的帧才能发布给消费者。
4. 不应仅凭屏幕“看起来正常”证明每个像素、末行、恢复及长期运行都正确。

这些是复用与复查线索，不是要求新对话先重新审计全部旧算法。

### 9.2 不应直接带入正式主线的内容

- FPGA 整网推理、卷积加速、权重复用等 `road_*` 研究实验。
- PC SegFormer 道路分割研究，不把它当作香橙派部署已经完成。
- 人工输入速度、距离、TTC 的演示，不当作实测速度或测距。
- FPGA 启发式车道/虚实线/斑马线结论，不继续作为正式道路决策主线。
- 旧 HUD、大红边、自动轮播等效果，不作为正式功能数量积累。
- 被否决版本、重复旧位流、临时试验构建入口。
- v11 的合成规则来源，不当作真实视觉驱动的变道告警。

保留归档不等于继续集成。测试图和诊断入口本身有价值，但要明确是测试数据，不能伪装成真实感知。

### 9.3 仍然没有完成证据的目标

在当前对话可确认的范围内，不能把下面内容写成已完成：

- FPGA 到香橙派的实体图像高速收发。
- 主工程的双目两路同时处理。
- 四路独立输入、完整缓存和低延迟上传。
- 新架构中的完整可配置 ROI/缩小/配置回读闭环。
- 香橙派的实际模型部署、车道与线型最终识别。
- 真实识别驱动的行停、变道与 LED 闭环。
- U 盘文件经香橙派解码、进入 FPGA、处理后返回的完整路径。
- 真实四视角标定融合与多路长稳性能。

## 11. 显示适配过程与当前版本状态

### 11.1 为什么出现 V5 系列

用户原来的 V4 及更早版本在普通显示器上能显示，但换用当前小屏后直接连接无显示，因此要求只改画面输出代码。

用户特别强调：

> “你直接改显示模块的代码就行，检查算法干啥？”

这条纠正需要传给下一对话：**发生显示问题时应优先围绕显示时序、输出和显示读出定位，不应无依据扩展为算法全量排查或改写。**

### 11.2 过程

1. 生成最初的 V5 小屏适配包。
2. 用户烧录后反馈花屏，并把路径改成全英文的 `JF\V5_MPI7001_800x480`。
3. 显示定向检查发现首帧同步启动问题：复位时帧同步保持高，读侧可能错过首个上升沿。
4. V5.1 令复位期间帧同步为低，保留首帧实际同步边沿，并在空白区加入顶部彩条、底部细棋盘用于定位输出链路。
5. 曾尝试的额外 PLL 拆分未进入最终交付；最终保持 V5 的时钟结构。
6. 用户上传画面并确认：**“现在是稳定的，就是画面有一些偏暗。彩边可以不要了。”**
7. V5.2 去掉检查图案，仅在 HDMI 显示端适度提亮，交付新的烧录文件。
8. **当前对话还没有用户烧录 V5.2 后的反馈。**

首帧同步问题是已复现并修正的缺陷，但不能据此说已证明它是最初持续花屏的唯一根因。V5.1 的稳定结论来自用户现场反馈，不是代理独立板测。
