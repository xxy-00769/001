# FPGA_GSV1 开发指挥与反馈约定

记录日期：2026-10-20。来源：用户在当前对话明确提出的协作方式。

## 1. 分工

- 本对话作为项目开发指挥与评审对话，按资深嵌入式项目负责人的工作方式，负责架构取舍、下发可执行提示词、检查执行证据、安排下一步。
- 另一个开发对话中的 AI 负责实际代码修改、针对性验证、构建和交付。
- 用户复制提示词到开发对话，再将执行结果及实际板上反馈带回本对话。用户自行烧录。
- 用户当前授权的是人工转交提示词的协作方式；不因此自动给其他对话发消息或创建新对话。

本文件记录本项目协作约定，后续本指挥对话应优先读取。不声称跨任意新对话自动具备记忆；新对话可通过 README 找到此记录。

## 2. 推进原则

1. 每轮围绕一个可验证的板上目标，给出范围和完成条件；优先打通数据流和操作闭环。
2. 按方案 V2 的 M1～M3 完成 FPGA 基础版，再做 M4 道路协同；四宫格稳定后单独安排 M5 全景。
3. 复用已验证模块，保留必要修复和相关检查；不反复全量盘点资料，不因为目录整理重建成熟 IP，不为以后可能需要的功能搭建大框架。
4. 每个功能改动必须说明“改了什么、有什么用、怎样测试、可见现象是什么”。没有可见变化也要说明实际验证收益。
5. 不允许以反复调参、重复跑同一验证替代进展。连续两轮诊断没有新增证据时，指挥侧调整假设、测试方法或实施路径；这不是允许跳过正确性检查。
6. 必要检查通过后交付；没有新问题不继续扩大验证。编译/时序/缓存正确性属于主链路条件，不能为了速度宣称通过。
7. 后续算法按场景设置验收目标。达标就接入系统，不无限追求指标；未达标则区分核心问题与增强项。仅非核心增强可以明确降级/延期，主链路问题必须解决或报告真实阻塞。
8. 不许用测试图替代真实输入并宣称完成，不许用固定标签替代视觉判断，不许把未烧录版本写成已上板通过。

## 3. 每次下发提示词应包含

- 本轮唯一主目标和版本标识。
- 需要读取的最少资料，以及可复用模块的位置。
- 必须实现的行为、暂不进入的功能及必要接口约束。
- 必要的仿真、构建和关键回归；出现问题时的排查与停止条件。
- 面向用户的实际交付格式与可观察验收步骤。

任务按实际依赖推进，不要求用户为常规实现选择反复确认；涉及必要硬件信息且无法从工程/资料确认时，只询问阻塞的具体信息，并继续独立工作。

## 4. 执行 AI 每次交付的固定内容

1. **本次改动：** 关键文件、实际新增/修复行为，以及对已有功能的影响。
2. **当前功能：** 区分已实现、构建验证、待上板、用户已确认；未完成项直接写明。
3. **构建证据：** 实际命令/入口、通过与否、关键仿真与时序/资源结果。未运行项标未运行。
4. **交付文件：** 可烧录文件的真实绝对路径、明确版本及生成时间；没有成功产物时明确说明，不提供旧文件冒充新版本。
5. **怎么测试：** 接线/显示规格、按键步骤、正常现象、失败现象；每步都可由用户直接操作。
6. **是否直观看到：** 是则说明画面/LED变化；否则说明通过什么统计、输出或测试才能证明，并说明必要性。
7. **遗留与下一步：** 仅列会影响后续推进的事项，说明推荐的下一步；不擅自扩展本轮范围。

建议执行 AI 最后附一个精简、便于用户原样复制的“回传指挥对话”摘要，包含版本、功能、构建、实际产物、待实测项及阻塞。

## 5. 用户回传模板

```text
【执行 AI 的交付报告】
粘贴其最终报告，保留版本、构建结果、产物路径、测试说明和未完成项。

【我的上板反馈】
烧录版本：
显示画面：
KEY5 前后切换：
KEY1～4 / LED1～4：
异常现象与触发步骤：
```

指挥侧根据回传给出三种处置之一：通过并下发下一任务；下发范围明确的修复任务；对真实外部阻塞给出所需输入和可独立推进项。不重复要求用户提供报告里已经有的信息。
