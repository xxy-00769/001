## 1. 结论与边界

用户提供的接口截图确实对应本地《MES50HP开发板硬件使用手册_1V1.pdf》扩展底板资源列表。该板有 HDMI-IN、HDMI-OUT、两个千兆以太网口、两个 SFP、PCIe x2、40pin IO、PMOD、USB 转串口等接口。

不必把四路视频输入全部限制为四个直接连接 DVP 的摄像头。可以将双目两路、HDMI 一路、网络一路汇总到同一块 FPGA。单板接口条件具备；四路独立输入、缓存调度、输出并行工作仍是需要开发验证的系统功能。

不能将“有两个镜头”当作配套例程已经实现双路并行，也不能将“有网口”当作已经能接任意网络摄像头。

2026 选题三原文（PDF 物理第 14 页）要求：

> 实现至少四路的视频流的并行采集与低延迟传输（模拟车的前、后、左、右），优化数据流带宽。

基础任务允许 HDMI、摄像头或其他图像输入接口。测评标准（物理第 15 页）另有图像拼接或融合、模拟汽车全景影像的要求。因此，可采用混合视频输入，但四个显示窗口、四路并行输入、真实四方位环视融合应分别验收。外部视频模拟方案是否满足全部高阶评分，由官方解释决定；本文不作官方认可承诺。

## 2. 推荐数据流

```text
双目左摄像头 ── DVP ──────────→ 输入通道 0 ┐
双目右摄像头 ── DVP ──────────→ 输入通道 1 │
电脑播放场景 A ─ HDMI-IN ─────→ 输入通道 2 ├→ 各路 CDC/FIFO
电脑播放场景 B ─ 自定义 UDP ──→ 输入通道 3 ┘       ↓
                                            DDR 帧缓存与仲裁
                                                   ↓
                                             缩放、画面合成
                                                   ├→ HDMI-OUT → 显示器（FPGA 处理结果）
                                                   └→ UDP 图像打包 → 香橙派
                                                                       ↓
                                                           重组帧、分视角、NPU 推理
                                                                       ↓
                                                          OSD、驾驶决策、告警显示
```

电脑的 HDMI 和 UDP 应提供两个不同场景，不要把一路画面复制两份当作独立来源。电脑用于产生可重复的模拟输入；后续也可以让香橙派发送一路已解码场景视频，但必须把“素材发送”和“FPGA 返回画面的识别”分成独立管线，防止误接成反馈循环。

网口规划有两种：

- 初期优先复用开源工程已接入的一组 RGMII，利用千兆全双工同时接收第四路视频、发送合成画面，通过交换机连接电脑与香橙派。收发方向各有带宽预算，不能把双向当成一个方向的 2Gb/s。
- 后期可以网口 0 输入、网口 1 输出，便于隔离和调试，但需要增加第二套 PHY/MAC/UDP 接口逻辑、IP/MAC 配置及约束。两个物理接口不代表项目已驱动两口。

HDMI 监视输出与网络发送应采用独立的缓冲和流量控制。网络拥塞时可丢弃待发送帧并计数，不应阻塞本地 HDMI 的固定输出时序。

### 3.2 当前公开版本的关键接线

在 `ddr_test_top.v` 约 677–715 行：

- `video0` 接 `pix_clk_in`、`zoom_de_out`、`zoom_data_out`，来源是 HDMI。
- `video1` 也接上述同一组 HDMI 信号。
- `video2` 接 CMOS1。
- `video3` 接 CMOS2。
- 紧随其后已经留有 `video1` 接 `rgmii_clk_0`、`eth0_rx_de`、`eth0_rx_data`、`eth0_rx_vs` 的另一组连线，但被注释。

因此，当前源码默认是“HDMI 一路复制为两个缓存输入 + 两路摄像头”。存在网络接收实现及预留接法，不等于当前默认版本已经四路独立输入。

恢复网络输入时应成组切换时钟、像素、有效信号与帧同步，不能只替换数据线。检查 DDR 读写调度对异步输入、断流、帧率不同和独立帧完成标志的处理，不能仅取消注释就宣布功能完成。`axi_m_arbitration.v` 的读仲裁存在成对服务结构，需要结合 FIFO 水位和帧完成行为仿真验证。

### 3.3 网络输入不是 RTSP

`eth_img_rec.v` 默认识别：

- 帧标志 `0xF05AA50F`。
- 分辨率信息 `{16'd960,16'd540}`。
- 随后的 RGB565 像素，每个 32 位数据字包含两个 16 位像素。

部分尺寸判断直接写成常量。更改分辨率时不能只改模块参数，必须检查所有计数终点、帧头判断、FIFO、缓存跨度和发送端格式。

输入格式需要专门的电脑/香橙派发送程序：视频解码 → 缩放 → RGB565 → 按协议分包 → UDP 发送。普通 IP 摄像头的 RTSP/H.264/H.265 数据不能直接交给这个像素接收模块。字节序、帧头位置、包内像素顺序和包间节奏都必须用抓包和测试图确认，不能仅凭常量值编写发送端。

接收模块主要按收到的像素数量推进状态，尚不能据此证明具备完善的丢包、乱序和帧超时恢复。正式版本建议引入帧号、包号、像素偏移、有效长度、超时及完整帧提交机制，并同步修改两端协议。

### 3.4 上位机缺失与移植工作

README 明确说本次只上传了 FPGA 设计，上位机代码当时留在另一台电脑；当前检出的目录也没有完整的 Linux 上位机应用、YOLO 推理和 ARM 软件工程。

所以“README 提到 gtk/ffmpeg、PCIe/以太网视频接收、YOLO 识别”只能说明项目总体设计，不能当作这些源码已全部公开。香橙派端应自行建立接收、重组、RGB565 转 RGB/BGR、RKNN 推理、OSD 和驾驶决策程序。

直接使用历史 `.sbit` 不能替代源码重编译验证。先核对器件、引脚、电压、DDR、PHY 和 HDMI 芯片，再处理 PDS/IP 版本迁移；先下载易恢复的配置进行测试，后续再考虑固化。

## 6. 香橙派传输接口选择

用户已明确授权按工程适用性选择接口，不要求必须使用网口。当前决策是：第一版采用千兆以太网，HDMI/USB 采集卡作为备选；只有实际图像细节和带宽需求超出前者能力时，才将 PCIe 升为主线。这个选择基于现有代码复用和当前画面预算，不是接口限制。

香橙派 5 官方 Wiki 明确列出 M.2 PCIe 2.0 x1、千兆网口、USB 3.0 和 HDMI 输出：https://www.orangepi.org/orangepiwiki/index.php/Orange_Pi_5 。这块 RK3588S 板的 PCIe 不能按其他 RK3588 板的 PCIe 3.0 x4 规划。MES50HP 的 PCIe x2 端点若接香橙派 x1 主机，需确认 IP 支持 x1 协商及实际接线，M.2 插槽也会被占用，不能同时默认留给 NVMe。Gen2 x1 扣除 8b/10b 编码后理论为 500MB/s，实际 DMA 吞吐更低，应实测；它仍有承载高分辨率原始视频的潜力。

香橙派的 HDMI 是显示输出，不能用一根 HDMI 线把 MES50HP HDMI-OUT 接到香橙派 HDMI 口完成采集。采用 HDMI 路线时必须另加采集设备，并确认其实际采集格式、USB 速度和 Linux 兼容性。

| 接口 | 适用性 | 实际工作 |
|---|---|---|
| 千兆以太网 | 第一版优先 | 自定义 UDP 原始像素，开发香橙派接收与完整帧重组；先低分辨率，实测丢包与延迟 |
| HDMI → USB 采集卡 → 香橙派 | 调试/备选 | Linux UVC 兼容、USB 带宽、实际输出格式与延迟要实测；需要同时监视可加 HDMI 分配器 |
| PCIe | 后期高带宽候选 | MES50HP 有端点接口，但需确认香橙派 5 实际引出接口、转接线、供电、参考时钟、复位、链路宽度及 ARM64 DMA 驱动；不是插线即可使用 |
| SFP 光口 | 板间或远端扩展 | 需要匹配的收发两端、光模块和协议；不能直接插到香橙派 RJ45 当普通网线 |
| 40pin / PMOD | 控制与特定扩展 | 通用 IO 本身不是现成的 Linux 视频输入口；高速图像连接还涉及电压、时钟、引脚和驱动 |
| USB 转串口 / JTAG | 调试与控制 | 不作为四路图像的主要传输通道 |

显示也要明确位置：MES50HP HDMI-OUT 直接显示的是 FPGA 合成/增强结果。如果想在同一画面看到香橙派生成的检测框，可由香橙派 HDMI 输出最终画面；若要求仍由 FPGA HDMI 输出，则需要将框坐标、文本/状态等结果回传给 FPGA 并做 OSD。回传结果携带输入帧号，避免在错误时刻标框。只把图像送到香橙派，不会使识别框自动出现在 FPGA 的显示器上。

## 7. 带宽和画质预算

纯像素载荷公式：`宽 × 高 × 帧率 × 每像素位数`。以下按 RGB565，不含网络头、帧协议、重传或冗余。

| 合成图像规格 | 纯像素载荷 | 千兆网络判断 |
|---|---:|---|
| 960×540 @30fps | 248.832 Mb/s | 适合第一版验证，仍需测 FPGA/系统有效吞吐 |
| 960×540 @60fps | 497.664 Mb/s | 线速预算可容纳，不代表现有代码已跑通 |
| 1280×720 @30fps | 442.368 Mb/s | 可作为后续画质目标，需适配 RTL 尺寸 |
| 1920×1080 @30fps | 995.328 Mb/s | 加上协议开销后无法通过单千兆口持续完整传输 |
| 1920×1080 @60fps | 1,990.656 Mb/s | 超过单千兆口能力 |

开源工程的 HDMI 默认输出结构是 1920×1080；以太网发送前另有一次缩小，打包模块默认 960×540。不要把“HDMI 1080p60”误读为“以太网 1080p60”，也不要把输出刷新率当作四路源各自的采集帧率。

960×540 四宫格中，每个视角只有约 480×270。初期可用于演示和大目标检测；远处行人、交通灯和车道细节可能不足。后续可增加逐路图像发送、重点视角 ROI 或独立分辨率策略。香橙派应保留视角编号，逐格切分后推理能减少跨格误检，并将检测框变换回合成图坐标。

## 8. 建议实施顺序与验收

1. **基线整理**：固定本次提交，保留许可证；核对实物板卡版本、工程器件、全部 IO/时序约束和 PDS/IP 版本。先重新构建最小 HDMI 链路，记录警告与时序结果。
2. **双目并行**：加入两套采集与独立缓存。左右镜头分别遮挡、移动不同图卡，确认一路变化不会影响另一路；记录各路帧率，不能只看两格有图。
3. **三路输入**：加入 HDMI，电脑播放带时间码/帧号的测试视频；两个镜头加 HDMI 各自保持独立更新，先验证四宫格中的三个独立来源。
4. **网络单路自测**：电脑产生固定 960×540 RGB565 图案，用明确的包协议送入 FPGA。先验证像素排列、字节序、行边界，再验证视频；添加超时与错误计数。
5. **接入第四路**：将 `video1` 从重复 HDMI 切到完整的网络信号组；确认四个不同来源均能持续更新。插拔网线或暂停发送时，其他三路与 HDMI 输出继续运行。
6. **FPGA → 香橙派**：复用/修订图像打包模块，先传 960×540@15fps，再测 30fps。核对发送帧号、收包数、完整帧率、丢帧、CPU 占用和持续运行温度。
7. **四路输入与网络输出并行**：验证同口全双工或双口隔离。记录每个方向吞吐及 FIFO 高水位，防止发送和接收互相饿死；做突发流量与断流恢复测试。
8. **NPU 和驾驶逻辑**：先静态图跑通 RKNN，再接实时帧，最后加入灯色、行人、障碍物、停止/转向/报警状态机。PC 上位机 YOLO 的实现不能直接当作 ARM NPU 实现。
9. **最终显示**：确定最终 OSD 在香橙派还是 FPGA；测量源画面变化到最终显示/告警的端到端延迟。展示四路独立输入、四宫格、识别、控制结果，并保存测试录像和日志。
10. **全景能力升级**：先用具有重叠区域的多视角素材验证标定、投影和融合；后续需要真实车周环视时，再增加合适的四个实际视角。双 FPGA 四摄像头方案留在此阶段比较成本和工作量。

最低验收矩阵：每路输入均有独立变化；任一路断流其余通道继续；网络丢包后恢复完整帧；本地 HDMI 不受网络阻塞；香橙派识别输入来自 FPGA 返回数据；采集、传输、推理、显示帧率分别记录；模拟全景与真实环视分别说明。
