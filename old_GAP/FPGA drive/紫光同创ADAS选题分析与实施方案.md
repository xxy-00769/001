> 版本 v1.0 ｜ 编制日期 2026-10-16
> 适用平台：紫光同创 PGL50H（盘古 50K / ALINX AXPGL50H 类开发板）

## 0. 结论先行：三个硬约束决定一切

先把最要命的事实摆在前面，方案的所有取舍都从这里推导。

| 约束 | 实际情况 | 直接后果 |
| --- | --- | --- |
| **时间** | 全国赛作品提交截止 **2026-11-04 18:00**；今天 **10-16** → 只剩 **19 天** | 不是"1~2 个月"，必须按 19 天倒排，且要留 1 天缓冲 |
| **人数** | 每支参赛队 **不超过 3 人** | 只能开 3 条并行线，没有第 4 个人做"打杂" |
| **平台** | 已确认：**小眼睛科技 盘古50K（工程代号 MES50HP）PGL50H-6FBG484**<br>42,800 LUT5 / 64,200 FF / 134 DRM / 84 APM / 296 IO / **HSST 仅 1 路** | 4 路 1080p 全算法链跑不下，必须裁剪；**PCIe 物理上只能 x1** |

**由此得出的结论：在 19 天 × 3 人的条件下，"4 路 + AI + 复杂场景"三件高阶全部做扎实是不可能的。**

评审依据的第一条是**「完成度、难度、工作量」**，完成度排在最前；而复赛/决赛资格取决于**初审（报告完整性、规范性）**。所以正确的打法是：

> **基础任务 100% 跑通闭环 → 高阶任务挑 2 项 ROI 最高的做 → 剩下的写成"设计已完成、受时间限制未展开"的清晰说明。**

这比"高阶做一半、基础有窟窿"的得分高得多。

### 高阶三项的 ROI 排序（这是本方案最核心的建议）

| 高阶任务 | 难度 | 演示效果 | 19 天可行性 | 建议 |
| --- | --- | --- | --- | --- |
| **① 4 路并行采集 + 4 宫格低延迟显示** | 中 | ★★★★★ 极直观 | 可行（D10 前完成） | ✅ **做** |
| **② ARM 端 AI 模型部署** | 中 | ★★★★☆ | 可行（用现成模型+框架） | ✅ **做** |
| **③ 复杂场景（夜间道路）** | 高 | ★★★☆☆ | 只做"FPGA 弱光增强"这一子项 | ⚠️ **部分做** |
| （题面举例的）PCIe 通信 | 极高 | ★★☆☆☆ | **19 天基本不可能** | ❌ **换以太网** |

**PCIe 为什么必须放弃：** 题面原文是"高速通信机制（**如** PCIe 接口）"——是举例，不是强制。而做 PCIe 需要：紫光同创 EP 端 TLP/Bar 逻辑 + ARM 侧 Linux 驱动 + 设备树 + DMA，任一项卡住就是一周。**19 天内这不是风险，是必然失败。**

替代方案：**千兆以太网（RGMII + UDP）**，带宽 ~110 MB/s，板载 PHY 有官方例程，3~5 天可通。报告中用带宽计算说明"满足系统需求"，并写明 PCIe 作为后续演进方向——这是站得住脚的工程决策，不是偷工减料。

## 0.5 现有资产盘点：`HDMI_DDR3_OV5640_test` 工程

**结论：这是一个可以直接复用为"基础任务 1"底座的高质量起点，省下约 5–7 天。**

### 它是什么

小眼睛科技（Meyesemi）盘古 50K 开发板官方例程包中的 **Demo 10**，原始路径 `MES50HP_v2/2_Demo/10_HDMI_DDR3_OV5640_test/`。

| 项目 | 内容 |
| --- | --- |
| 器件 | **PGL50H-6FBG484**（Logos 系列） |
| 工具链 | **PDS 2022.1**（Fabric Compiler build 99559） |
| 顶层模块 | `hdmi_ddr_ov5640_top` |
| 功能 | OV5640 摄像头 → DDR3 帧缓存 → HDMI 显示，**完整的采集-缓存-显示闭环** |

### 通路结构（每一级都是可复用的积木）

```
OV5640 (DVP 8bit)
   │  cmos1_/cmos2_ 两套接口，板上都有连接器
   ▼
cmos_8_16bit.v      8bit → 16bit RGB565 位宽转换
   ▼
wr_fram_buf / rd_fram_buf   SDPRAM 乒乓缓冲（IP 核）
   ▼
DDR3_50H             DDR3 控制器 + PHY（硬核，32bit DQ / 15 行 / 10 列 / 3 Bank）
   ▼
rd_buf → sync_vg     读缓冲 + 视频时序发生器
   ▼
ms72xx_ctl / ms7200_ctl / ms7210_ctl   MS72xx HDMI 发送芯片 I2C 配置
   ▼
HDMI 输出（r_out/g_out/b_out 各 8bit + pix_clk + vs/hs/de）
```

### 对竞赛方案的四点直接影响

| 发现 | 影响 |
| --- | --- |

### 摄像头时钟参数（可直接抄进约束）

```
create_clock -name cmos1_pclk -period 11.900    →  84 MHz
create_clock -name cmos2_pclk -period 11.900    →  84 MHz
```

84 MHz PCLK 对应 OV5640 的 720p 级别输出。若改用 640×480@30（方案推荐），PCLK 约 24–27 MHz，时序压力更小。

### 1.1 官方评审依据（来自 socchina.net）

1. 完成度、难度、工作量
2. 适用性、创新性
3. **平台结合程度、利用程度、综合性能指标**
4. 报告完整性、规范性（**初审**）
5. 作品现场演示状态、能力测评结果、答辩表现（**复赛/决赛**）

### 1.2 逐条翻译成设计意图

| 官方说法 | 真正想要的 | 我们的应对 |
| --- | --- | --- |
| 平台结合程度、利用程度 | **必须让人看出这是 FPGA，不是拿 FPGA 当转接板** | 所有像素级运算（滤波/边缘/投影/帧差/形态学）全部做成 FPGA 流水线，用并行度和延迟数据说话 |
| 软硬协同 | **分工要有道理，不是随便切一刀** | 按"每帧都要跑的低延迟预警→FPGA；低频语义识别→ARM"这条线切 |

| 创新性 | 别只做"例程拼接" | 三个创新点：行级流水低延迟、边缘计算省带宽、FPGA 弱光增强 |

### 1.3 关键提醒：**"综合性能指标"和"报告规范性"是最容易白捡的分**

大部分队伍把时间全花在调硬件上，报告只写个大概。你们要在 D15 就开始积累数据，D17 之前把"资源占用报告 + 时序报告 + 性能指标表"三张表做出来。**初审只看报告，报告不行连决赛都进不去。**

### 2.1 数据流与带宽预算（答辩要用）

| 环节 | 参数 | 计算 |
| --- | --- | --- |
| 采集 | 4 × 640×480@30fps | 4 × 9.2M px/s ≈ **36.9 Mpx/s**，PGL50H 轻松 |
| 像素时钟 | 单路 ~27 MHz（含消隐） | 4 路共 ~108 MHz，远低于器件能力 |
| DDR3 帧缓存 | 4 × (640×480×2B) × 2 乒乓 ≈ 4.9 MB | 1GB 富余；带宽需求 ~74 MB/s（写）+ 74（读） |
| **显示端到端延迟** | 行缓冲直通设计 | **< 1 帧（< 33 ms）**，实测目标 < 20 ms ← 核心卖点 |
| FPGA→ARM | 只传 ROI 小图 + 结果 | 4 路 × 320×240 灰度 @5fps ≈ **3.8 MB/s**（千兆的 3%） |
| 对比：全画幅上传 | 4 路 640×480 RGB565@30 | 55 MB/s，占满千兆 → **所以必须边缘计算** |

> **这段带宽对比就是"为什么要在 FPGA 上做处理"的答案**，答辩时直接讲这条逻辑链。

### 2.2 资源预算（**基于实测基线**，不再是拍脑袋估算）

手里那份 `HDMI_DDR3_OV5640_test` 工程提供了宝贵的**实测锚点**。它是单摄像头 → DDR3 → HDMI 的完整通路，PDS 布局布线报告给出的实际占用是：

| 资源 | 该 Demo 实测占用 | PGL50H 总量 | 占用率 |
| --- | --- | --- | --- |
| LUT | 3,039 + 2,106 = **5,145** | 42,800 | **12%** |
| FF | 3,083 + 1,942 = **5,025** | 64,200 | 8% |
| DRM（块 RAM） | 18.5 | 134 | 14% |
| APM（DSP） | 0 | 84 | 0% |
| IO | 125 | 296 | 43% |
| HSST | 0 | **1** | — |
| DLL | 1 | 10 | 10% |

> 数据来源：`place_route/hdmi_ddr_ov5640_top.prr` 的 Device Utilization Summary。

**这条基线推翻了"资源不够"的悲观判断**：一条完整的「DVP 采集 + DDR3 帧缓存 + HDMI 输出」通路只吃 **5.1K LUT（12%）**，DDR3 PHY 和控制器大量使用硬核，软逻辑开销很小。按此外推 4 路系统：

| 增量模块 | 估算 LUT5 | 说明 |
| --- | --- | --- |
| 基线通路（采集+DDR3+HDMI）×1 | 5,145 | **实测值**，可作为共享底座 |
| 追加 3 路采集通路 | +4,500 | 每路 ~1.5K |
| 灰度 + 3×3 中值 + Sobel ×4 | +8,000 | 主算法链 |
| 车道线 / 斑马线 / 帧差形态学 | +8,000 | 三识别 |
| 4 宫格拼接 + OSD 叠加 | +3,000 | 缩放 + 图层混合 |
| 以太网 MAC + UDP | +2,500 | — |
| RISC-V 软核 | +2,000 | 配置与调度 |
| **合计** | **≈ 33K / 42.8K ≈ 77%** | ✅ **可行，但余量不多** |

**结论：4 路可以冲，但必须遵守两条纪律**

1. **主视角（前、后）跑完整算法链；辅助视角（左、右）只做采集 + 显示 + 帧差。** 全 4 路跑全算法链会到 ~45K，超出器件。这个"因资源约束主动做功能分级"的决策要写进报告——它体现的是真实工程能力，是加分项。
2. **目标分辨率定 640×480@30（或 720p@30 只给前向一路）。** 4 路 1080p 不是 PGL50H 该干的事。
3. **IO 要提前算**：单条通路已吃 125/296 IO（43%），再加 3 路摄像头（每路约 14 根）约 +42 → 167/296（56%）。可行，但**自制转接板时要避开 DDR3 和 HDMI 占用的 Bank**。

### 2.3 关键硬件事实：HSST 只有 1 路

PGL50H-6FBG484 的 `Use of HSST` 总量是 **1**。这意味着：

- PCIe **物理上只能做到 Gen1/Gen2 ×1**（单 lane），理论 5 Gbps，实际可用约 200–400 MB/s
- 相比千兆以太网的 ~110 MB/s，**PCIe 只快不到 4 倍，但开发工作量是 10 倍以上**（EP 逻辑 + Linux 驱动 + 设备树）

**这就是放弃 PCIe 的硬性技术理由**，比"时间不够"更有说服力。写进报告：*"经评估，PGL50H 仅集成 1 路 HSST，PCIe 方案为 ×1 链路，相对千兆以太网的带宽增益不足以抵消其开发与集成成本，故选用以太网作为主通信链路，并将 PCIe 列为后续演进方向。"*

## 3. 通信方案：为什么最终选以太网

| 方案 | 实测带宽量级 | 开发周期 | 判断 |
| --- | --- | --- | --- |
| PCIe Gen1/Gen2 x1（HSST 硬核） | ~200–400 MB/s | **3–6 周**（EP 逻辑 + Linux 驱动 + 设备树） | ❌ 19 天不可行 |
| **千兆以太网 RGMII + UDP** | **~110 MB/s** | **3–5 天**（有官方例程） | ✅ **主用** |
| SPI | ~10 MB/s | 1 天 | 备选 |
| UART | ~1 MB/s | 半天 | ✅ 指令 + 遥测 |

**最终方案：**
- **以太网 UDP**：FPGA → ARM 传 ROI 灰度小图 + 检测结果框；ARM → FPGA 回传 AI 结果
- **UART**：控制指令下发 + 状态遥测回传（低速率、高可靠，与图像通道解耦）
- **PCIe**：写入报告的"后续演进"，附一段"若采用 PCIe 的带宽提升预期"分析

> 附注：PGL50H 的 HSST 高速收发器支持 6.375 Gbps、PCS 支持 PCIe Gen1/Gen2 协议，硬件条件是具备的——只是**开发周期**不允许。这个说法在答辩时既诚实又专业。

## 4. 功能实现对照表（赛题要求 → 我们的做法）

| 赛题要求 | 实现方式 | 落在哪一层 | 优先级 |
| --- | --- | --- | --- |
| 图像采集-处理-显示闭环 | DVP 采集 → DDR3 乒乓 → HDMI 输出 | FPGA | **P0** |
| 斑马线识别 | ROI 内边缘密度 + 行列投影的**周期性纹理**判定（斑马线有强周期特征，比边缘密度可靠得多） | FPGA 实时 | **P0** |
| 行人识别 | 帧差 → 形态学去噪 → 连通域标记 → 长宽比/面积过滤出候选框；ARM 端 YOLO 做语义确认 | FPGA + ARM | **P0** |
| 路障识别 | 帧差 + 车道 ROI 内区域方差突增 + 底部位置先验 | FPGA | **P0** |
| 虚线变道 | 车道线边缘列投影的**周期性**判虚实；仅虚线区允许变道，实线区变道触发告警 | FPGA | **P1** |
| 超速提醒 | 车速来源：电位器/串口模拟 → 与阈值比较 → 蜂鸣器 + OSD 告警 | RISC-V / FPGA | **P0** |
| 碰撞提醒 | 前车距离（视觉测距或超声波）→ 计算 TTC，TTC < 2s 告警 | FPGA + ARM | **P1** |
| 打转向灯 | 按键/拨码输入 → LED 指示 + OSD 箭头叠加 | MCU | **P0** |
| 4 路并行采集与低延迟传输 | 4×DVP → DDR3 乒乓 → 4 宫格 HDMI；行缓冲直通 | FPGA | **P1（高阶）** |
| 复杂场景（夜间） | 直方图均衡 + 伽马校正 + 中值降噪 | FPGA | **P2** |
| AI 模型部署 | NCNN/RKNN + YOLOv8n（320×320，INT8） | ARM | **P1（高阶）** |

**软硬协同的分工逻辑（答辩主线）：**
> "凡是**每帧都要跑、延迟敏感**的像素级运算，放 FPGA 做全流水并行；凡是**计算量大但可以低频调用**的语义识别，放 ARM 做。FPGA 负责'永远在线的反射神经'，ARM 负责'偶尔思考的大脑'。"

## 7.5 立刻要做的第一件事：把手上这个工程跑起来

**不要先动代码，先验证硬件是好的。** 今天（D1）就能完成：

1. **直接烧比特流**：`generate_bitstream/CMOS1.sbit`（或 `CMOS2.sbit`）已经编译好了，用 PDS 的下载工具烧进去，接上摄像头和显示器，看能不能出画面。**这一步成功 = 硬件平台验证通过**，整个方案的风险立刻下降一大截。
2. **再打开工程**：用 PDS 2022.1 双击 `HDMI_DDR3_OV5640_test.pds`。`.pds` 内用的是相对路径（`source/rtl/...`），理论上能直接加载。
3. **如果工程加载报"文件缺失"**，原因是 `pds.log` / `impl.tcl` 里残留了作者机器的绝对路径（`C:/Users/w/Desktop/...`）。处理办法：
   - **首选**：在 PDS 里新建一个工程，用 `add_design` 把 `source/rtl/` 下的文件逐个加进去，约束文件用 `hdmi_ddr_ov5640_top.fdc`，器件选 `PGL50H-6FBG484`。约 20 分钟。
   - **不要**直接用 `impl.tcl` 跑批处理——里面全是失效的绝对路径。
4. **验证双摄像头**：把顶层 `define CMOS_1` 改成 `CMOS_2`，重新编译，确认第二个摄像头也能出画面。**这是 4 路方案的第一个技术门槛**。
