# V5：MPI7001 显示输出适配

现场反馈更新：用户烧录后有画面但明显错块、偏色与杂点，V5 显示验收失败。用户将包移动到 `E:/zhoumian/FPGA/JF/V5_MPI7001_800x480`。后续排查见 [V5.1 记录](13_mpi7001_v5_1_diagnosis.md)，下文保留 V5 原始设计与自动检查的历史证据。

日期：2026-10-20。基于当前工作副本的 V4 功能，按用户授权只调整显示链路，并由用户手动烧录。未操作 JTAG 或 Flash。

## 问题和输入证据

用户已成功通过 JTAG 下载 V4，但连接 MPI7001 后无显示。用户截图中 Windows 的活动信号为 800×480、59.98 Hz。

本机注册表保存的 `DISPLAY/MPI7001/.../Device Parameters/EDID` 共 256 字节，两个 128 字节块的校验和均为 0。首选详细时序为：

| 项目 | 有效区 | 前肩 | 同步宽度 | 后肩 | 总数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 水平 | 800 | 16 | 80 | 96 | 992 |
| 垂直 | 480 | 1 | 3 | 13 | 497 |

EDID 像素时钟 29.57 MHz，水平同步正极性、垂直同步负极性。EDID 是 Windows 保存的记录，非 FPGA 在线读取。原显示为 1280×720，像素 PLL 实际约 37.1212 MHz；原代码中“37.125”的注释及旧 FDC 的 67.5 MHz 声明不能当作真实频率测量。

时序不兼容是此次修复假设。用户还需检查显示屏独立供电、HDMI-OUT 接口及线缆；编译和仿真不能代替屏幕点亮验收。

## 显示方案与范围

摄像头、图像处理、KEY8 六档、帧标签、完整 1280×720 写入、DDR bank 所有权和错误恢复逻辑保留。

DDR 读侧增加可选 `DISPLAY_HALF`，默认 0，V5 顶层设为 1。显示时读原图第 0、2、…、718 行；每行仍读完整 1280 像素，在原生成的行 RAM 中选取第 0、2、…、1278 列。输出为 640×360，在 800×480 中从坐标 (80,60) 开始显示，左右各 80 黑像素、上下各 60 黑行。保留完整视野、16:9 比例，属于最近邻抽样，不是平滑缩放，也不是裁去视野边缘。

物理显示有效区 DE 始终覆盖 800×480，黑边属于有效区。画面是否健康只决定 RGB 是否显示摄像头内容，不改变 HDMI 扫描尺寸。DDR 完成初始化后即输出显示时序，第一帧未准备好时为黑色。

使用新 `pll_mpi7001` 包装原有版本的 `GTP_PLL_E3`，没有升级或重新生成 DDR/摄像头 IP。参数为输入分频 5、反馈 130、输出分频 44/130/52：VCO 1300 MHz，输出约 29.545454 MHz、10 MHz 和 25 MHz。后两路保持既定的配置/摄像头标称频率。显示帧率约 59.9270 Hz，相比 EDID 首选时钟偏低约 0.083%。实际接受范围须上板确认。

FDC 将像素时钟如实声明为 sys_clk×13/22，并修正 25 MHz 约束目标为真正使用的 `u_pll.clkout2`。未放宽时钟周期、uncertainty 或增加 false path。原工程的 IO/CDC 覆盖限制仍在。

## 验证和失败记录

本机 ModelSim 2020.4 安装存在，但无法取得授权。首次静默安装仿真器的命令被自动审批拒绝；之后使用 MSYS2 官方仓库下载并解压的便携 Icarus Verilog 13.0，存放在工作空间临时目录，没有依赖该安装命令或修改 ModelSim 授权。

1. 时序定向仿真覆盖连续 3 帧、每个时钟的读请求坐标、有效区、同步极性和两周期对齐，PASS。
2. 原厂 PLL 模型仿真检查锁定、像素/配置/摄像头输出周期，PASS。
3. 最终定向验证范围为生产 `rd_buf` 和屏幕时序：native 读返回 BFM 提供已知源像素，保留原生成的读行 RAM 及原厂 DRM 模型，检查连续两帧全部 640×360 像素、隔行命令地址、每行 80 返回拍、末行及循环 RAM 回绕、像素与屏幕同步/有效区对齐。未重新验证写侧、所有权、旧图像算法、坏帧拒绝或故障恢复。最终结果见发布记录，不把工具失败计为通过。
4. 首轮完整 PDS 生成位流，但快角摄像头处理域有一条 hold 路径 −0.001 ns，未发布。证据目录 `../tmp/v5_mpi7001/20261020_124155/`（相对工程父目录）；目录中的通用 SBIT 不是交付版本。
5. 第二轮尝试提高 PNR 保持时间修复目标，但时钟树修复目标 350 ps 超过工具允许的 0～200 ps，PDS 拒绝执行 PNR；此轮不发布。
6. 时钟树修复目标恢复为 200 ps，数据路径修复目标从 200 ps 增至 350 ps，最大迭代从 16 增至 24，在新独立目录重新构建。只改变物理实现修复策略，不改变约束或算法。最终状态见发布记录。
7. 上述布局仍在旧诊断逻辑相邻延迟寄存器之间留下 −0.001 ns hold 违例。读取本机 `help pnr` 确认 `-gplace_seed` 用法后，以布局种子 2 重建，原违例消失，但 DDR 内部另有 −0.035 ns hold；种子 3 在旧诊断逻辑留下 −0.005 ns hold。均未发布，没有修改这些算法或屏蔽路径。
8. 种子 4 同时启用工具支持的 `-enable_route_constraint_iterate -route_constraint_iterate_times 3 -route_constraint_slack 0.05` 进行布线修复复核；最终状态以发布记录和最终时序报告为准。

早期 Icarus 仿真不是通过记录：包含全部旧算法的慢速用例主动停止；简化输入夹具首先修正了帧开始标签锁存；原厂 RAM 包装在 Icarus 下出现全零数据。最小八字 RAM 用例复现了全零失败：生成包装的 CSA/CSB 两个 `always @(*)` 在当前参数下只赋常量，没有敏感输入，因此不会执行。仅在临时仿真副本中将这两个块改为 `always_comb` 以获得时间零初始化，八字 RAM 用例通过，但集成写侧仍出现未知值，未声称整链路问题已解决。没有为通过而修改生产写侧/IP，改为直接验证本轮新增的输出读侧。原厂 `GTP_DRM18K` 模型、地址/数据/时序逻辑及 PDS 使用的全部 IP 文件保持原样。最终读侧仿真明确标为兼容副本下的结果，不能称为原始包装在 Icarus 无修改运行通过。专用读侧测试还纠正了复位阶段人工帧脉冲被时序源持续高电平遮蔽的夹具问题；该次失败不计通过。

仿真使用外部 native-port 存储 BFM，不覆盖物理 DDR PHY、电缆、MS7210 模拟链路或显示屏本体。既有 no-clock、外部 IO、宽泛异步时钟分组等限制继续保留，不能把约束下通过称为全 IO/CDC 签核。

## 用户验收

1. 给屏幕独立供电，将开发板 HDMI-OUT 接到屏幕 HDMI 输入。
2. 在 Fabric Configuration 关联交付目录中命名的 V5 SBIT，通过 Boundary Scan → Program 下载；不要继续选择 V4。
3. 默认应出现居中的原始摄像头画面，四周有黑边。显示分辨率为 800×480，视频内容为 640×360。
4. 每隔约一秒按一次并释放 KEY8，核对原图、灰度、中值、Sobel、颜色候选、旧诊断六档循环。检查四边、末行、颜色及持续运动，不应错列或持续冻结。
5. 若不显示，区分屏幕提示“无信号”和“已识别输入但全黑”，反馈屏幕提示、HDMI 初始化 LED、相机是否连接，以及烧录文件名。JTAG 下载成功不等于显示已通过。

本次不写 Flash；断电后需重新下载，除非另行固化选定版本。
